# Working implementation

Status: compiler extraction, native queries, and saved-file coordination are implemented development slices, tested on macOS/Apple Silicon. This is not a complete v0.0.1 release. [DESIGN.md](DESIGN.md) defines the agreed scope; [COORDINATOR.md](COORDINATOR.md) describes background operation and its limits.

Xcode follow-on: project/internal-workspace inputs deduplicate and report an explicit partial planner gap. Saved `.xcscheme` and `.xcconfig` inputs participate in common invalidation. The installed CLI returned incompatible contexts across identical requests and is not used for serving graphs; an optional external BSP experiment is authorized, with no adopted runtime dependency. See [evidence and boundaries](XCODE_PROVIDER.md).

## Build and run

```sh
bash scripts/build.sh
bash scripts/test.sh
# Optimized artifacts and matching tests:
bash scripts/build.sh release
bash scripts/test.sh release
target/debug/know-code watch /absolute/repository
target/debug/know-code coordinator status
target/debug/know-code index /absolute/repository --configuration Debug
target/debug/know-code query /database/path/from/output/index.db '{"op":"symbols","name":"Greeter"}'
```

Build/test scripts default to `debug` and accept `release`. Rust and the bundled SQLite build use the selected Cargo profile; the .NET worker and smoke consumer use matching Debug/Release artifacts. The coordinator selects the worker matching its compiled core. Node smoke packages are staged separately under `.artifacts/build/{debug,release}/node/`; the existing `bindings/node/know_code.node` development copy remains Debug. Matching .NET native libraries sit alongside each managed smoke consumer. Both profiles can coexist without swapping binaries. This is checkout-based development staging, not release distribution packaging.

The product's own build profile is separate from the indexed workspace's C# configuration. A Release Know Code build still analyzes a workspace registered as Debug using its Debug compilation settings. `scripts/test.sh release` exercises the same compiler/native/coordinator/preparation/resolution suites with optimized artifacts; `KNOW_CODE_BUILD_PROFILE` is its developer-test selector. For performance comparisons, `scripts/benchmark-index.py --profile debug|release` chooses the matching host and provider and records the analyzed configurations. The login installation remains as documented in [LOCAL_INSTALL.md](LOCAL_INSTALL.md).

The locked build uses Rust 1.99.1, Node 24.22.2, .NET SDK 10.0.403, and Python 3 in the tested environment. Cargo.lock, package-lock.json, and NuGet lockfiles pin dependencies. The build restores dependencies but does not install toolchains. At the user's explicit request, development toolchains were installed under `~/.cargo`/`~/.rustup`, `~/.dotnet`, and `~/.local/share/nodejs`, with command links in `~/.local/bin`.

Rust/C# protocol types are generated from [analysis.proto](../proto/analysis.proto); JS loads that same schema. C# generation reuses Cargo's pinned native ARM64 protoc. Grpc.Tools 2.72.0 attempted to launch an Intel-only generator and was removed; Rosetta is not required. Generated code remains in ignored build directories.

`watch` persists registration and starts the coordinator when absent. `index` requests a full refresh through the same coordinator and returns database/generation JSON. The coordinator survives consumer disconnects and resumes registrations after restart. Default state lives under `~/Library/Application Support/Know Code/`; `KNOW_CODE_DATA_DIR` isolates development/tests. The host resolves [runtime resources](PACKAGING.md) relative to its executable or an explicit override; target/debug and target/release development layouts remain supported without compiled-in checkout paths. Separate local runtime/npm/NuGet candidates are verified outside the checkout. Ordinary index/watch commands do not install a login job. The separate [runtime installer](INSTALLATION.md) manages an owned login service and compatible runtime updates/rollback while retaining product data on uninstall. It refuses the existing checkout-based development job.

## Implemented behavior

- One Rust core crate with ordinary modules for protocol/facts, storage, updates, workspace inputs, queries, and the shared control client. Thin host/C ABI/Node targets reuse it. Native watching is a host dependency, not a required embedded-core dependency.
- Agent-launched stdio MCP with explicit-workspace auto-registration through the shared CLI attachment path. Focused tools and structured caller/callee/impact reads use existing Rust operators; bounded hash-guarded source excerpts are shared across CLI/MCP/.NET/Node. SDK dependencies remain host-only; tracing is compiled off. See [workflow, protocols, execution bounds and remaining gaps](MCP.md).
- Shared live freshness certification in the common Rust control client, with optional immutable state pages, live-owner/input gates and ordinary RPC fallback. Setup/I/O failure preserves baseline indexing; certificate lifetime is bounded by the coordinator writer fence. Published code contains no prototype counters or diagnostic control operation. Capable peers use bounded, coalesced one-way activity notifications, including first requests; activity delivery is best effort under overload and never establishes freshness. Older peers retain first/five-second RPC checkpoints. See [contract and verification](LIVE_FRESHNESS.md).
- Experimental Swift and Rust adapters begin the planned v0.0.3 slice while remaining v0.0.1 work continues. They do not change release acceptance. Node workers, including TypeScript, share [Protobuf framing](../providers/shared/protocol.mjs); compiler LSP/BSP clients share [bounded JSON-RPC transport](../providers/shared/jsonrpc.mjs). Neither adapter adds storage or query logic.
- [Swift](SWIFT_PROVIDER.md) uses the selected Swift compiler's IndexStore for standalone directory modules and SwiftPM targets. SwiftPM's official build server owns target/source/compiler-setting planning and indexing-only module preparation. Dependency restoration uses common checkpoints/progress; build-tool plugins and unprepared external macro tools remain explicit gaps. Per-target exact settings deduplicate, native records spool per job, and fact emission stays bounded. The small native reader loads matching toolchain IndexStore and is built for each Debug/Release profile. Xcode remains a [researched follow-on](XCODE_PROVIDER_RESEARCH.md); ordinary compiler errors, unsupported inputs and missing toolchain settings remain visible rather than being replaced with standalone inference.
- Swift selection prefers a compatible installed Xcode for unpinned projects, preserves explicit process overrides and recognized repository pins, and uses active CLT when Xcode is absent. One provider resolver selects coherent compiler/SDK environments per project and records the choice in coverage; it never changes global selection or installs tools. Saved `.swift-version`, `.tool-versions`, and `.xcode-version` files use shared invalidation. Existing indexes need refresh to adopt a provider-policy upgrade; automatic tool-installation/policy-change detection remains incomplete. See [pin/override scope and limits](SWIFT_PROVIDER.md#toolchains-state-and-limits).
- [Rust](RUST_PROVIDER.md) uses repository-selected rust-analyzer semantic navigation over Cargo workspaces, with explicit partial coverage for configuration/build-script/macro/generated-source gaps. Cargo metadata deduplicates member manifests inside the adapter. Cargo restoration is not yet implemented by the product; real-corpus testing prepared a copied workspace separately. The common coordinator discovers/watches all four providers' source/configuration inputs and uses the same atomic publication path. Swift manifests, versioned manifests, Cargo configuration and compiler-reported header/modulemap inputs participate in invalidation. `.build`, `.build-*`, `DerivedData` and `.worktrees` join ordinary discovery exclusions; explicitly reported saved inputs retain the existing override path.
- TypeScript 5.9.x compiler-backed named symbols and identifier references, including aliases and locals. Configured projects load repository-selected TypeScript. Files outside configured project roots also receive inferred compilation units, grouped by package boundary; files owned by configured projects are excluded from inference. Query coverage exposes language-specific `analysis_options`, including inferred grouping/options. Standalone files may use pinned provider TypeScript 5.9.3 with inferred settings. Unsupported versions fail explicitly; malformed explicit config is never silently replaced with inference. Transient views with one real compiler root now share declaration identity/signature; multiple-root views remain distinct. The isolated worker collects completed compiler programs between contexts, without changing embedding-host GC. See [identity, measurements and limits](TYPESCRIPT_PROVIDER.md).
- Roslyn 5.9 symbols/references using repository-selected installed SDK project evaluation. The SDK compiler assembly version must match the provider's Roslyn assembly version. Every declared target framework is analyzed sequentially in one workspace configuration. Roslyn/MSBuild negotiates compatible referenced contexts; a lazy input catalog and one active compilation closure avoid retaining all compiled variants. Standard SDK assembly-identity metadata is evaluated in a short-lived SDK tooling mode of the same provider binary, batching every target of one project in its fixed invocation directory. Planning/restoration finishes before complete metadata and compiler inputs are cached. Fresh project/import state between targets observes version hooks that change imports; selected SDK assemblies are compile-only references resolved through Locator. The helper reuses the worker Protobuf codec and has no storage/query responsibilities. Identical identity properties allow all of a project's target variants to share one Roslyn load; differing metadata or an ambiguous target mapping falls back to separate loads. Actual Roslyn inputs also supply discovery: unknown dependencies are prepared first and the root is reloaded; known dependencies avoid a redundant discovery pass. Every target retains distinct facts and dependency identities. SDK selection is checked once per distinct nearest `global.json` scope per worker request; nested pins remain explicit checks. Workspace selection follows repository/MSBuild defaults or an explicit override, including selected solution-to-project mappings; see WORKSPACE_SETTINGS.md and FIRST_WAVE_CONTRACT.md. Differing SDK selections within one worker request remain explicitly unsupported.
- C# jobs load requested compiler definitions first, then prefer roots sharing the most project contexts with the active closure. The workspace removes projects outside the next closure and retains shared immutable compiler state. Both workspaces are disposed at job completion; workers still exit between jobs. This is compiler work reuse, not skipped target analysis or a byte-based memory cap. Loader diagnostics without project IDs are associated with the owning load's roots, so unrelated contexts do not inherit them. See [measurements and limits](INDEXING_PERFORMANCE.md#c-compiler-reuse-within-one-job).
- Ordinary project documents and compiler-generated C# documents, including virtual source-generator output. Source positions convert once per file to half-open UTF-8 byte ranges. The C# worker retains only one file's offset-conversion map at a time. Its emitter also caches symbol IDs by object reference for the current source file, clearing symbol references after each file; fallback location anchors are formatted only for symbols without documentation IDs. Public identities, semantic binding, target separation, and compiler diagnostics are unchanged. See [allocation measurements](INDEXING_PERFORMANCE.md#c-symbol-id-allocation-pass).
- For direct, member, and conditional-member invocations, the C# adapter queries the invocation for an exact ordinary/extension/local-function method, avoiding the method name's full method-group construction. Other cases retain name lookup, including callable variables/members, explicit delegate `Invoke`, dynamic/ambiguous calls, and unsupported syntax. Normalization and the original name's source range remain unchanged. This adds no compiler residency or call-graph relationship extraction. See [verification and measurements](INDEXING_PERFORMANCE.md#c-invocation-reference-lookup).
- Worker/control protocol v7 over bounded Protobuf framing: four-byte little-endian length, 8 MiB maximum frame, 128-occurrence fact batches. A source payload currently occupies one frame; oversized payloads abort the job and preserve prior publication. Providers never write SQLite or execute graph queries.
- Shared preparation checkpoints and progress messages over that same worker protocol. Rust retains setup outcomes centrally next to each index, including failed attempts; providers own restore commands and effective package/MSBuild paths. Source-only saves reuse outcomes. Watcher overflow/rescan requests rehash and reconcile saved inputs without forcing analysis or a restore; only an explicit refresh requests an unconditional preparation retry. Dependency/configuration changes or explicit refresh can retry; missing successful outputs trigger preparation again. Failed restore diagnostics can accompany completed partial compiler graphs, while worker/protocol failures preserve the prior publication.
- npm 10–11 and pnpm 10–12 preparation honors exact repository pins, acquires missing supported tools into a shared verified user cache and handles nested/workspace packages. Repository-selected scripts/hooks require an explicit personal workspace grant. Unsupported families are actionable gaps; no manager substitution. See [accepted scope and evidence](FIRST_WAVE_CONTRACT.md) and [trust/settings](WORKSPACE_SETTINGS.md).
- The C# adapter evaluates per-target assets paths with the active configuration, including centralized `UseArtifactsOutput`, and retains bounded stdout/stderr error details. Status exposes the current restoration/analysis stage through all native consumers.
- SQLite 3.54.1 bundled through rusqlite 0.41.1/libsqlite3-sys 0.39.1, WAL, foreign keys, and a 2 MiB page-cache setting per workspace connection. Rebuildable index synchronization uses NORMAL; registry metadata/manifests use FULL. A page-cache setting is not a total-process memory cap.
- Index format v6 retains interned occurrence/relationship symbol/artifact keys and adds per-callsite relationship evidence, capability reports and exact project-definition pointers/snapshot witnesses and receiver-specialized dispatch evidence; API identities remain unchanged. Generation manifests reference compilation-owned facts. Unchanged symbols/occurrences/source are reused rather than copied into each publication. Changed projects and recorded transitive dependents are reanalyzed; structural/configuration changes can request a full refresh. Formats v1/v2 first migrate integer keys transactionally; v3 relationship triples migrate as legacy_unknown evidence. Formats v2/v3/v4/v5 remain readable during lazy upgrade through the same operators; new writes use v6. Old graph capability coverage is unknown, not complete. Existing WAL readers retain their original facts/source while unreferenced state is reclaimed.
- [Portable pagination](CURSOR_INTEGRATION.md) now connects the shared generation/registry/quota primitives to coordinator startup, personal settings, streamed result files and actual publication. Common-core native queries compute once and serve frozen pages, source and context in-process from one pinned generation. The coordinator owns leases/files and evicts idle cursors under one shared logical retention pool; failed cleanup stays charged. Restart/unregister invalidate tokens explicitly. This assembled slice passed focused Debug/native/MCP/installed-offline validation at a24d1ce; see the linked evidence and limits. It is not final release certification.
- Source payloads deduplicate by SHA-256 within a workspace database, preserving artifact provenance and compilation ownership. FTS5 indexes symbol names/signatures. Source-body string/comment search is unassigned backlog work, not a 0.0.1 gate; symbol/signature ranking tuning remains a separate implementation concern.

- SQLite read views enable QPSG before preparing queries to avoid parameter-triggered replanning of nested graph views. Writers retain their existing settings. Graph adjacency keeps large optional evidence behind `Box`, preserving serialized fields and native ABI while reducing temporary buffer size. - Symbol search chooses fixed, bound SQL shapes for exact names, text and browsing. Exact names seek the existing name index; text drives symbol rowid lookups; both preserve generation/compilation ownership and optional target scope. - [Workspace clients](WORKSPACE_API.md) in .NET and Node open repository roots through shared Rust registration/bootstrap, with status/progress, refresh/wait, typed errors and client-only disposal. ## Freshness and remaining limits

The [0.0.1/0.0.2 release-readiness ledger](RELEASE_PLAN.md) maps remaining work to existing requirements without changing release scope.

Native queries use the shared Rust control client to certify eligible live state on every request. Capable peers receive best-effort one-way activity notifications; older peers retain RPC activity checkpoints. Uncertain/pending live state and failed submissions use the existing RPC and wait up to 500 ms by default for captured observed inputs. They then read SQLite in their own process. `freshness_wait_ms` is configurable up to 120,000; `deadline_ms` now defaults to 5,000 ms (maximum 120,000) across native queueing, freshness control, SQLite, traversal/projection and core JSON encoding. Expiry returns `deadline_exceeded`; graph search limits can still return partial findings before that deadline. A later save cannot keep extending the captured target. Result metadata distinguishes current/stale/unverified and retains coverage/diagnostics and source identity. Coordinator loss makes managed data stale, never fresh. No usable prior index returns not-ready.

Current describes acknowledged observed inputs, not instantaneous knowledge of every concurrent filesystem write. [Overall query deadlines](QUERY_LIFECYCLE.md) now use shared cooperative enforcement and release expired readers. Complete core JSON responses now default to 256 KiB and are configurable through response_max_bytes from 1 KiB to 2 MiB; over-budget output returns response_limit_exceeded without dropping required metadata. Raw Rust ReadView results use the same byte counter. General query admission/peak memory, pagination packing and generation-pinned expiring cursors remain pending. Each current native call owns one read view and releases it after materializing its result. Source referenced by an expired/reclaimed view is not promised indefinitely across separate requests.

Incrementality currently means affected-project reanalysis and storage-unit reuse. C# compiler objects can be reused between compatible root closures within one job; compiler processes still restart between jobs. Across-save compiler sessions and finer invalidation remain future work. [Shared resource control](RESOURCE_CONTROL.md) now enforces sampled coordinator-wide CPU/memory limits and workspace indexing cancellation; the accepted defaults are two cores and 2 GiB, with personal overrides. Active reconciliation still scans the selected workspace's relevant input files. Toolchain/package changes outside tracked inputs may require an explicit refresh; broader installation/version-change detection remains unfinished.

Compiler-selected TypeScript/Roslyn project bodies now link through the common graph operators, with exact definition pointers, snapshot checks and per-path compilation selections. Compiler-selected cross-project interface/virtual candidates now share receiver-specialization and composition-snapshot guards through Rust/.NET/Node; broader dispatch coverage remains partial. Native hosts share the same behavior. See [call/impact contracts and remaining limits](CALL_GRAPH.md#compiler-selected-project-bodies); reference-selection capability is distinct from partial call/dependency/dispatch coverage.

Remaining v0.0.1 work includes broader dispatch/structured graph coverage, inline graph body projection, cross-target grouping, dependency integrity/version-change detection, general query admission, corruption rebuilds, upgrade cutover and final distribution/transport acceptance. The accepted npm/pnpm preparation, shared workspace settings and initial runtime installation slices are implemented; see FIRST_WAVE_CONTRACT.md and INSTALLATION.md for actual evidence and limits. Yarn remains unassigned backlog work. Cold setup/analysis uses one shared workspace slot with bounded process-group termination and coherent publication. No Know Code usage collector or uploader has been added; personal/debug recording remains unimplemented.

`coordinator login-plist` emits reviewable LaunchAgent XML with RunAtLoad/KeepAlive and toolchain PATH. The generator does not install/activate a service. The user explicitly approved this machine’s development installation; it is installed and running as documented in [LOCAL_INSTALL.md](LOCAL_INSTALL.md). It references the current executable/checkout and is separate from product release packaging.
