# Draft 0.0.1 acceptance criteria and execution plan

Status: draft for focused Q&A, revised after [three independent read-only audits](RELEASE_ACCEPTANCE_REVIEW.md). The intended finish line is a fully validated, publish-ready 0.0.1 candidate, followed by the user's separate publishing decision. This draft derives requirements from [DESIGN.md](DESIGN.md), the accepted decisions in [AGENTS.md](../AGENTS.md), and the implementation/gap inventory in [RELEASE_PLAN.md](RELEASE_PLAN.md). It does not start a goal, freeze unresolved choices, or certify the current implementation.

Every release criterion needs an observable outcome and evidence tied to the final source/artifacts. Existing tests and historical runs below are starting points for that evidence, not automatic passes. An unavailable required measurement stays open. Moving a requirement to a later release, changing an accepted threshold, or replacing a required measurement needs an explicit user decision.

## Scope and interpretation

0.0.1 includes compiler-backed TypeScript/C#, in-process .NET/Node, local CLI/stdio MCP, saved-file indexing, the accepted query/storage/operational model, and a usable shared runtime distribution for macOS ARM64. Architecture must retain one Rust engine across deployments and future languages. A production shared-server deployment is not added to this release.

0.0.2 retains cross-repository queries, company onboarding, Angular template references and refactoring continuity. Swift/Rust source-language acceptance remains 0.0.3, despite experimental adapters already in the tree. Embeddings, searchable history, full optional third-party source indexing and MCP HTTP remain unassigned. Unsaved editor buffers remain outside the product's freshness boundary permanently.

An accepted requirement with an unresolved mechanism remains required; it is not permission to invent an extra product surface. Documented partial compiler coverage must be evaluated against agreed cases, not an impossible claim of complete runtime semantics. Syntax-only analysis cannot satisfy compiler-backed requirements. The implementation's known limits are neither blanket waivers nor automatic new release blockers.

## Proposed subagent workflow

Use four active slots: the primary agent as integrator, two bounded implementers, and one independent reviewer. This is a proposed operating plan, not an instruction to launch agents before the contract is agreed.

A source baseline is needed before parallel writes: the initial audit found no HEAD and untracked source. Review the intended source inventory, exclude generated/cache/reference-clone artifacts, and establish a source checkpoint before deriving isolated worktrees. Read-only audits can proceed without a source commit. Keep worktrees/artifacts in durable locations, and leave the working installation/original corpus repositories under their existing authorization boundaries.

Each implementation task has one behavior/AC subset, a baseline revision, owned paths/contracts, explicit exclusions, focused checks, and a small handoff. Shared protocol/schema/query contracts have one named owner. Agents propose conflicting contract changes to the integrator before changing them. No agent may replace another's edits, rewrite shared history or weaken an AC to obtain a pass. New packages/abstractions require a concrete need and review under the existing simplicity requirements.

Independent worktrees isolate source, generated files, native staging and test data. Do not share a mutable Cargo target directory, node_modules, worker outputs or SDK smoke binaries. Use isolated coordinator sockets/state/login labels; disable reusable compiler/build servers for sandbox-isolated .NET consumer tests as already documented. Shared immutable tool/dependency caches do not establish shared validation evidence.

The reviewer checks behavior, invariants, failure cases, evidence and complexity, including the integrator's substantive fixes. It may identify missing checks; implementation of those checks belongs to the task owner. A reviewer is not a second uncoordinated writer in the same worktree. The integrator owns cross-task contracts, integration order and the final validation record. An agent's own passing branch tests do not certify the assembled candidate. Verify that worktree/environment settings really isolate outputs: `build.sh` replaces node_modules and stages native smoke binaries, and protocol generation writes into the provider tree.

Recommended first pair: **C09 package preparation and C06 C# build-context planning**, after a small integrator-owned contract checkpoint.

The source baseline and concrete additive worker interfaces are documented in [FIRST_WAVE_CONTRACT.md](FIRST_WAVE_CONTRACT.md). Shared settings/control wiring and both adapter slices are integrated; source-bound worker, SDK and package evidence is recorded there. The R02 correction has passed independent review, completed segmented Debug coverage and refreshed Debug package/install validation; exact evidence is linked in RESOURCE_CONTROL.md. Optimized-profile and remaining release gates are open. No release acceptance is claimed.

### Test ownership and cadence

1. During development, task owners run focused behavior/invariant checks in their own worktrees. Reuse existing harnesses; do not build one validator or test framework per AC.
2. Before integration, the reviewer evaluates the change and its evidence. Each handoff names the exact source revision, tests/commands/profile, fixture identity, artifact paths, failures and remaining gaps.
3. The integrator merges sequentially and runs checks for affected cross-task boundaries. Fix discovered problems with focused tests before requesting another broad run.
4. Once implementation and review settle, freeze the release candidate and run the full Debug integration checkpoint. Run the agreed optimized/native/package/platform/real-encoding gates against the identified candidate. Agents can continue read-only or isolated future work, but cannot mutate the frozen validation tree.
5. A release-gate code fix creates a new candidate. Invalidate the affected evidence, repeat focused checks, then recertify the final frozen candidate. Do not present a full-suite result from an older revision as a run on the new one. Formatting/docs-only changes need impact-appropriate checks, not an automatic compiler-suite loop.
6. One coordinator owns expensive integration/performance jobs. Do not run several full suites or unrelated heavy builds during a benchmark. Real encoding remains intentional competing load; extra agent workloads must be controlled/labeled.

An AC may reuse a shared test and evidence bundle. It does not need a custom validator, benchmark or subprocess. Test changes that correct a mistaken expectation are reviewable; changing an agreed behavior/threshold to hide a failure is a product decision.

## Draft goal completion contract
