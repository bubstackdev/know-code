# Xcode provider follow-on research

Status: read-only feasibility work, after the user's selected **SwiftPM first,
then Xcode** order. No Xcode adapter, preparation policy or supported-version
floor is accepted by this document. No project builds, package manifests,
scripts or generators ran, and global `xcode-select` was not changed.

## Installed prerequisites

The active developer directory is `/Library/Developer/CommandLineTools`, but
`/Applications/Xcode.app` is installed and responds using a per-command
`DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` override. Searches
also checked `~/Applications`; no second Xcode was found there.

- Xcode 27.2, build 27B52, with Apple Swift 6.4.2.
- Bundled Swift compiler, SourceKit-LSP and `libIndexStore.dylib` exist in the
  Xcode toolchain.
- `xcodebuild -showsdks` lists iOS/device and iOS Simulator 27.2, macOS 27.2,
  and other Apple platform SDKs. An SDK listing does not prove an installed
  simulator runtime/device or a successful project compilation.
- Xcode includes `SwiftBuild.framework`, its build service and `swbuild`
  executable. Presence does not establish a stable third-party import/ABI:
  the inspected framework has no public `Modules` directory.

An Xcode adapter must select a coherent compiler/SourceKit/IndexStore/SDK set,
check required SDKs and report absent or incompatible prerequisites. It should
not require changing global selection merely because CLT is active. Exact
supported Xcode releases remain a product decision. Raw version/help/SDK
evidence and the unchanged global selection are in
[environment.json](../.artifacts/xcode-probe/environment.json).

A separate SwiftPM metadata probe also found a practical distinction: this
installed CLT planner can drop its Testing macro search option between cold and
warm sessions, even with the same compiler/SDK explicitly selected. Scoped
Xcode sessions returned identical complete options, including Testing plugin
paths, in both sessions. This is metadata evidence only; it does not prove
semantic extraction or establish a global toolchain default. See
[full argument comparison](../.artifacts/swiftpm-plugin-probe/toolchains/1794000603883/comparison.json).

## Actual supplied project shape

Read-only `plutil`/XML inspection used the existing durable `atelier-app`
snapshot, not the original repository. `AtelierLibraryPhone.xcodeproj` has:

- An app target with 24 listed Swift sources and a UI-test target with one.
- A shared `AtelierLibraryPhone` scheme including that UI-test target.
- Debug/Release configurations, Swift language mode 6.0 and iOS deployment
  target 27.0; project `SDKROOT` is `iphoneos`.
- Three local Swift package references: repository root, `Phone` and `Remote`.
- No shell-script phases or scheme pre/post-actions in this snapshot.

This is an iOS compilation context with local package dependencies and tests.
The user requires both device and simulator code paths. Each must have its own
compiler/SDK context and provenance while identical source payloads share storage;
graph paths must not combine incompatible contexts. This requirement does not
establish SDK, destination or architecture defaults beyond those two contexts.
Analyzing those files as a standalone macOS directory or copying flags from a
different SwiftPM target would not establish project semantics. Workspaces,
schemes, targets, configurations, SDK/destination/architecture and source
membership need explicit provenance. Package facts compiled for different
platforms must not be merged just because their source text matches.

[project-metadata.json](../.artifacts/xcode-probe/project-metadata.json) records
the parsed targets, package paths, configuration settings and metadata hashes.
The project was not passed to `xcodebuild`, `swbuild` or another planning tool.

A read-only scan of all three originals confirms one primary-repository saved
scheme: `AtelierLibraryPhone`; no saved user scheme-management files were found.
The initial current-scheme test therefore uses that scheme, including its tests.
This does not establish an all-schemes product policy. Dependency schemes under
aether-kit's `.build-ci/checkouts` and nested `.worktrees` were excluded from
the count; virtual/autogenerated schemes were not evaluated by project tools.
[Original scheme inventory](../.artifacts/xcode-probe/original-schemes.json)
records the scope. Discovery must avoid accidentally enrolling these dependency
and nested-worktree projects; excluding only a literal `.build` directory would
not cover `.build-ci`.

## Tooling paths worth proving

| Path | Evidence and useful boundary | Remaining proof |
| --- | --- | --- |
| Official Swift Build planning API | Upstream exposes `loadWorkspace` for Xcode project/workspace containers, workspace information, build-description-only operations and per-file indexing settings. | Establish a compatible pinned API/service combination, execution controls and small distribution cost. Installed private framework presence alone is insufficient. |
| Xcode-aware BSP bridge | Reuse Know Code's shared JSON-RPC/BSP client and existing fact/IndexStore path; obtain real target/source/compiler settings from an external planner. | Validate planner behavior, preparation scope, pinning, dependencies and resource use; do not blindly accept generated commands. |
| Existing build logs / compiler index | Can import user-produced settings/artifacts without initiating an application build. | Prove freshness and source/configuration identity; a previous successful build is not evidence for current saved inputs. |
| `xcodebuild` build-setting queries | Installed help documents `-showBuildSettings -json` and `-showBuildSettingsForIndex`. Useful discovery/status evidence. | They are not, by themselves, a proven complete per-file compiler-argument feed. Reconstructing the whole build engine from settings is outside this proposal. |

The official [Swift Build project](https://github.com/swiftlang/swift-build)
is used by Xcode and SwiftPM. Its
[session API](https://github.com/swiftlang/swift-build/blob/main/Sources/SwiftBuild/SWBBuildServiceSession.swift)
separates workspace loading, build-description creation and indexing-file
settings, and exposes external-tool-execution preferences/delegates. This is
the strongest upstream planning lead. It does **not** yet prove that loading or
planning an arbitrary project runs no repository code, nor that upstream `main`
matches this installed Xcode service. The source package is a substantial
build-system dependency; avoid embedding a new engine into Know Code's core.

SourceKit-LSP's official [BSP integration
guide](https://github.com/swiftlang/sourcekit-lsp/blob/main/Contributor%20Documentation/Implementing%20a%20BSP%20server.md)
defines target/source enumeration and per-file SourceKit options separately
from target preparation. That contract fits the shared worker boundary;
Xcode does not require a separate graph/query engine. Compiler options and
prepared modules must describe the same context.

Two upstream-owned reference implementations illustrate the options:
[sourcekit-xcode-bsp](https://github.com/slime-studio/sourcekit-xcode-bsp)
uses Swift Build and advertises Xcode 26+/macOS 15+ prerequisites; its early
status and companion service bundle need evaluation before adoption. Those
are that project's requirements, not accepted Know Code minimums.
[xcode-build-server](https://github.com/SolaWing/xcode-build-server)
instead obtains settings from build logs and documents rebuilding to refresh
them. The latter is an optional artifact-import lead, not justification for
automatically building applications on every save. No reference implementation
was installed, built or copied into Know Code.

## Suggested next proof, after SwiftPM

Use a tiny owned Xcode fixture under `.artifacts/xcode-probe/` to prove only
workspace/target enumeration and per-file indexing options. Include a script
marker and verify planning leaves it untouched. Then compare app and test
target options, SDK and source ownership against the copied supplied project.
Keep caches/derived data central and isolate any allowed package restoration
from analysis. Missing generated sources/modules should yield an explicit
partial graph until bounded preparation is implemented.

The likely direction is a narrow planner adapter feeding the existing Swift
extraction path, preferably through the shared BSP contract. Choosing a
particular bridge, invoking preparation, destination defaults and packaging
remain open decisions. This reconnaissance establishes available prerequisites
and concrete APIs; it makes no project-resolution or performance claim.
