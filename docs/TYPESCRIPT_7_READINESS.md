# TypeScript 7 readiness — scope correction

Checked 2026-11-12. The user identified omitted TypeScript 7 support and confirmed it as a required 0.0.3 release gate ahead of optional estate work. This records accepted release priority, dated findings and the implementation checkpoints below; it is not release certification.

## Shipped boundary

Know Code 0.0.2 supports TypeScript **5.9.x**. The provider pins 5.9.3 for its own compiler fallback; configured repositories select their installed compiler. The shipped worker explicitly rejected other version families. TypeScript 6 and 7 are therefore not supported by 0.0.2. Rejecting unsupported compilers is honest behavior; it does not make the compatibility gap acceptable indefinitely.

[analysis.mjs](../providers/typescript/analysis.mjs#L20) depends on the existing JavaScript compiler API, including configuration parsing, compiler-host/program creation and type-checker access. Graph extraction depends on those compiler objects. Relaxing the version check or changing the package pin is not evidence that TS7 semantics work.

## Upstream evidence

- Microsoft released TS7.0 on July 8, 2026 as a native Go implementation. Its launch announcement says it does not ship an API and describes TS6 side-by-side compatibility for older tools. That launch statement must not be read as proof that later 7.0 packages expose no native API surface. [Official 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/).
- The October 20, 2026 TS7.1 beta announcement documents new synchronous/asynchronous clients, AST/filesystem entry points, snapshots and explicit native-resource disposal. This is a different API with a beta support boundary. [Official 7.1 beta announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/).
- Exact published [TS7.0.2 package metadata](https://registry.npmjs.org/typescript/7.0.2) exposes `./unstable/sync`, `./unstable/async`, `./unstable/ast` and `./unstable/fs` (plus related subpaths). [TS7.1.0-beta metadata](https://registry.npmjs.org/typescript/7.1.0-beta) uses promoted paths such as `./sync`. For both audited packages, the root export is `./lib/version.cjs`, not the legacy compiler API. Metadata is retained at `.artifacts/ts7-readonly-audit/official-packages-01/`. These are candidate integration surfaces, not passing compatibility checks or a guarantee for all 7.0 patches.

The native 7.0.2 unstable exports make an exact-version integration plausible without a compiler fork; usable semantic and graph parity still need proof. Do not assume the beta establishes stable 7.1 availability or that a 7.1 analyzer silently satisfies a repository pinned to 7.0. API availability, stability and exact compiler-version support are separate questions. No full-build or indexing speedup is inferred from these findings.

## Read-only adapter findings

The three agents inspected current extraction plus exact official native package metadata/types/source. The JavaScript package archives were retained and integrity-checked as inert reference material; they were not installed or imported, and no native compiler binaries were downloaded or executed. Evidence: `.artifacts/ts7-readonly-audit/official-packages-01/FINDINGS.json`.

The current provider has seven adaptation surfaces: compiler selection, configuration/source ownership, AST/coordinates, declaration identity/signatures, calls/implicit operations, generic dispatch evidence and compiler-selected project links. This suggests narrow compiler-session/extraction changes, not a generic compatibility framework or a second fact/query engine.

- The new API's declaration/signature handles and compact symbol/type references are not interchangeable with legacy live AST objects. Resolve them within their owning session/snapshot; native IDs must not become durable public identities. The available instantiated-target operation does not replace current multi-root symbol semantics. See [current canonical identity rules](../providers/typescript/symbols.mjs) and the retained native declarations.
- **Highest-risk gap:** neither inspected native surface supplies the current resolved-reference/source-redirect ownership hooks. Projects/configuration paths and supplied references do not prove which compilation/source bodies the compiler actually consumed. Preserve [project-link proof requirements](CALL_GRAPH.md); missing evidence is an explicit boundary, never a guessed pointer or a silent weakening of existing guarantees.
- Exact TS7.0.2 LSP source implements call hierarchy and rich navigation. Those are useful, but call hierarchy does not provide all dependency kinds, implicit classifications, receiver specializations or selected-context fingerprints. LSP alone is not demonstrated parity. [Pinned server](https://github.com/microsoft/typescript-go/blob/2bd066d87f5bafd315be9f40889d0a60b9e58e0b/internal/lsp/server.go), [pinned call hierarchy](https://github.com/microsoft/typescript-go/blob/2bd066d87f5bafd315be9f40889d0a60b9e58e0b/internal/ls/callhierarchy.go).
- Prefer probing the exact 7.0.2 native compiler API first. Its snapshots, project ASTs and checker operations offer a plausible route for local semantic extraction, but batched IPC costs, lifetime cleanup and graph proof still need runtime measurement. [Pinned API](https://github.com/microsoft/typescript-go/blob/2bd066d87f5bafd315be9f40889d0a60b9e58e0b/_packages/native-preview/src/api/async/api.ts).
- The inspected 7.1 beta transport defaults batch response pages to 300,000,000 bytes and permits an individual response to exceed a page limit; it also exposes external content-mapper and optional timing-collection settings. Do not inherit those settings blindly or treat the outer worker frame limit as a bound on inner compiler-client allocations. Preserve bounded extraction, existing trust rules and published-build zero-telemetry requirements. [Exact beta options source](https://raw.githubusercontent.com/microsoft/TypeScript/3e9236361fa97a9e6c685f4833ac457ae2d8c50a/packages/typescript/src/api/options.ts). Beta details must not be assumed to describe the 7.0.2 client without inspection.

TS6 is a separate, likely smaller compatibility task: Microsoft states API compatibility with 5.9, while documenting changed compiler defaults and resolution behavior. Verify those actual selected-compiler semantics instead of imposing 5.9 defaults or rewriting repository configurations. [Official TS6 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/). The user subsequently accepted the 0.0.3 matrix of **5.9.x, 6.0.x and explicitly tested TS7 releases**; that initial audit had not yet proven actual TS6 runtime compatibility.

## Proposed first work

1. Inventory the compiler API surface used by existing configuration, identity, occurrence, call/dependency and project-link extraction. Retain current 5.9 support while assessing native integration.
2. Pin actual compiler artifacts for a focused feasibility check. Establish a truthful route for repository-selected TS7.0 separately from the new 7.1 API; an LSP path may have different evidence/capability limits and must be evaluated rather than assumed sufficient. Honor repository pins and report unsupported combinations without compiler substitution.
3. Prove symbols/references, useful signatures/source extents, call/dependency evidence and exact source/context ownership through the existing worker/fact contract. Preserve compiler errors, unsupported forms, project-reference context witnesses and generated-source boundaries. Do not claim support from a successful type-check or diagnostic-only run.
4. Reuse language-neutral framing, storage, queries, scheduling and resource controls. Keep the native compiler behind the analysis-worker boundary; no new Go query engine or required Go runtime inside embedded graph libraries is justified. A narrow compiler API adaptation is preferable to copying the TypeScript engine or creating a generic compatibility framework.
5. Measure actual indexing/saved-update latency, native subtree memory/CPU, snapshot disposal and cancellation. Upstream full-build speedups are not Know Code indexing performance results, and upstream concurrency defaults must not silently multiply the shared budget.
6. Extend relevant existing fixtures and installed-package acceptance after the path is proven. Include exact compiler selection/failure, configured/inferred projects, calls/impact, saved updates, project links and preserved 5.9 behavior. Avoid repeating the entire historical suite for this initial audit.

## Accepted release consequence

The accepted TypeScript matrix is 5.9.x, 6.0.x and explicitly tested TS7 releases. TS7 is required for 0.0.3 and takes priority over optional estate search. Reassess capacity with Swift/Rust/Xcode also required; do not silently drop confirmed requirements or promise that all work fits. Exact TS7 release pins and the integration approach remain to be proven; prerelease API availability does not itself make prerelease compiler support a required public promise.

The initial audit used only local source inspection, inert package inspection and official-source browsing. The subsequent finite runtime probes below are separate evidence; they do not turn the initial audit into a full compatibility run.

## Focused runtime probes — 2026-11-12

Exact official TS6.0.2, TS7.0.2 JavaScript API and its matching Darwin ARM64 compiler package were provisioned under `.artifacts/ts7-feasibility/toolchains/`. **TS6:** a copy of the existing TypeScript worker with only its compiler guard widened to include 6.0.x passed initial and saved-input analysis of three referenced projects plus an inferred group. It checked exact 6.0.2 selection, distinct Unicode locals/ranges, alias calls, value/type relationships, compiler-selected project fingerprints, saved symbol replacement and valid partial facts after a compiler error. Initial output contained 34 symbols, 66 occurrences and 39 relationships; the saved/error case contained 36/70/41. The first two attempts stopped during experiment dependency setup; those failures and controller corrections are retained. This is worker feasibility, not installed/native acceptance or proof of all TS6 configurations.

**Native TS7.0.2:** the actual selected native compiler and shipped unstable API completed a bounded owned fixture for AST/source access, aliases, Unicode byte ranges, resolved call/signature declaration handles, saved-file updates with the prior snapshot retained, and explicit snapshot/API disposal. Clean basic and positive-reference contexts had no compiler diagnostics after completing the fixture's minimal global declarations. The caller Program actually exposed its consumed dependency source/body. With source redirect disabled and no declaration output available, it did not expose that source and reported compiler error 6305. Receipts: `.artifacts/ts7-feasibility/native7-probe-01/run-02/{result.json,runner.json}`. The earlier observation with incomplete fixture globals is retained as run-01.

The native probe did **not** emit Know Code facts, establish generic/multi-root identity parity, prove independently indexed project-body composition, benchmark indexing or certify product resource enforcement. Its outer deadline/log bounds and tiny fixture do not impose a hard limit on the native client's internal transport. `getResolvedProjectReferences` and source-redirect witness accessors were unavailable; independently indexed dependency linkage remains explicitly unproven. Representing compiler-consumed dependency bodies inside the caller's own context is a separate design candidate, not an adopted replacement for existing project-link guarantees.

No production provider code changed during these probes. Shipped support remains 5.9.x until implementation and matching acceptance are completed.


## Worker implementation checkpoint — 2026-11-12

Integration source now selects repository TypeScript 5.9.x and 6.0.x through the legacy compiler API and exact native 7.0.2 through its unstable synchronous API. No other 7.x version is promised. Selected package `exports` are resolved within the actual package boundary; an unavailable/broken/unsupported selected compiler does not fall back to an ambient installation. Native extraction uses the same fact/relationship protocol and shared Rust storage/query path.

The native worker checks configured/inferred saved sources, aliases/calls/value/type dependencies, Unicode local identities and UTF-8 ranges, generic declaration roots, distinct constructor parameter/property identities, saved compiler-error partial facts and changed fingerprints. Declaration handles resolve in the actual caller Program. Compiler-consumed dependency source remains in that caller's context; disabled redirects preserve the missing-source boundary. Independent project definition pointers, generic dispatch and full graph parity remain unavailable/partial. Synthetic views without a unique compiler-proven semantic root are omitted with diagnostics rather than guessed.

Focused worker result: `.artifacts/implementation-0.0.3/wave-01/native-typescript-worker-03/` at `786b6e4`. Existing semantic identity/alias/generic/dispatch-key regressions passed against exact 5.9.3 and 6.0.2 on that same source: `typescript-59-semantic-02` and `typescript-60-semantic-02`. The selected-package resolver's eight pure boundary cases passed separately. Earlier failed native setup/canonicalization investigations remain retained.

These are compiler-worker checks, not stored/native/installed acceptance or indexing performance certification. The native API's inner transport does not expose a hard per-response allocation cap in this exact version. Coordinator process-group resource enforcement, actual memory/cancellation behavior, full input ownership and installed workflow gates still need evidence. The assembled CLI/.NET/Node graph fixture has been extended for exact 7.0.2 and awaits a matching build/run.
