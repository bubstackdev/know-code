# Shared analysis limits and cancellation

The user accepted initial automatic ceilings of **two CPU cores' worth of background work and 2 GiB of memory**, adjustable per user. These are ceilings, not reservations or hardware requirements. The user also accepted **20 ms sampled memory enforcement**, including possible overshoots between checks, and cancellation that resumes on the next saved change or explicit refresh.

## Operating contract

One coordinator-wide governor uses the existing single active analysis slot across repositories and providers. Ordinary modules in the Rust core implement limits, cancellation, worker ownership and publication checks; adapters retain compiler/toolchain semantics. No new dependency or separate language scheduler was added. The governor includes the coordinator's process footprint/caches and compiler descendants; limits are not multiplied per repository or compiler context. A monitor exists only while a job is active and stops when the analysis session ends.

CPU accounting sums the live process tree and exited-child CPU charged back to live ancestors. A shared CPU balance carries across scheduled workspaces, allowing a small burst of up to 100 ms times the configured core count. Workers run in owned process groups; the monitor stops/continues those groups when the balance is exhausted/replenished. Cooperative checks also throttle Rust discovery, hashing and staged ingestion. Control/query coordination threads remain available: the coordinator process itself is never suspended, and its LaunchAgent/QoS policy is unchanged. This is sampled rate control, not a hard kernel quota on every coordinator thread. Query execution in embedding applications remains outside this background CPU controller.

On Apple Silicon, libproc CPU counters use Mach ticks. Conversion uses the installed system timebase, not a fixed tick frequency or an assumed nanosecond counter. The first synthetic load test caught that incorrect assumption before acceptance. Process accounting uses Apple's [libproc API](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.h); the kernel's [child-accounting implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_resource.c) includes exited descendants in their parent's counters. Live-tree enumeration can race child exit; accounting favors conservative throttling during counter handoff.

Memory enforcement compares the sum of `ri_phys_footprint` with the shared limit approximately every 20 ms. This sum is conservative and is not a unique-page measurement of total system RAM. It includes coordinator overhead and compiler helpers; it does not include arbitrary allocations in .NET/Node embedding hosts. Exceeding the limit stops the affected analysis and preserves the previous coherent generation explicitly stale. There is no automatic cap increase or incomplete-stream publication. Sampling cannot guarantee an instantaneous RAM ceiling, reclaim all coordinator baseline memory, or prevent allocation bursts between observations. If required accounting/monitor setup is unavailable, analysis fails resource-limited rather than silently running unbounded.

A stop resumes any throttled group, requests termination and escalates to kill after 200 ms if necessary. Cleanup also kills remaining group helpers after the worker exits. The leader is observed with `waitid(...WNOWAIT...)`; its PID remains reserved until the monitor stops signaling that group and cleanup/reaping finish. This avoids signaling an unrelated process through a reused group leader PID. Managed .NET helpers inherit disabled MSBuild server/node reuse. The owned provider process tree is a lifecycle boundary, not a security sandbox against arbitrary daemonizing executables; intentionally escaping/reparenting helpers are not an enforcement guarantee.

## Personal settings and entry points

```sh
know-code resources
know-code resources --cpu 1.5 --memory-mib 1536
know-code cancel /absolute/registered/workspace
```

The first command reports effective defaults/settings and starts the installed coordinator if needed. Mutations use the same shared Rust control client and Protobuf socket endpoint as registrations. Settings live in `resources.json` under the central user data directory, outside source repositories. The coordinator validates and serializes changes, writes/syncs an atomic replacement and then applies the policy. Unknown JSON fields, nonpositive/nonfinite CPU values and invalid memory sizes are rejected. Uninstall retains this file with the rest of product data.

Changing CPU/memory policy does not change compiler options or invalidate healthy graph facts. Changes apply to active work at the next measurement. Updating policy retries resource-limited work; it does not resume explicitly cancelled work. Repeating unchanged settings does not trigger new jobs. This first automatic mode enforces the accepted fixed ceilings; dynamic OS-pressure tuning remains future work.

Node exposes `await workspace.cancelIndexing()`; .NET exposes `await workspace.CancelIndexingAsync()`. Both use the common Rust client. Cancellation is explicitly workspace-wide and affects the shared background job. Closing/disposal, MCP disconnect and canceling a query waiter do not stop shared indexing. Idle cancellation is a no-op; queued cancellation stops compiler launch and reports `cancelling` until its saved-input baseline is recorded. `unwatch` cancels active work for the removed registration.

Accepted queued and active cancellations first report `cancelling`, then `cancelled` after a scan-only job records the baseline. Memory/accounting failures report `resource_limited`. `WorkspaceStatus.outcome_code` preserves a machine-readable reason alongside the human error through CLI, both SDKs and query coordination metadata. Prior facts remain stale; without a usable generation queries remain not-ready. Ordinary compiler-error partial graphs remain a different, successful publication outcome.

SQLite setup and publication preparation use the same cancellation controller through SQLite interruption. Interrupts repeat while stopped, covering the race where cancellation precedes statement execution. Cancellation and the final commit share a lock. Cancellation accepted before publication prevents cutover; a successfully committed generation wins if cancellation arrives afterward. An already committed coherent graph is not undone. Index cancellation is distinct from per-request SQL/native query cancellation, which remains unfinished.

Cancellation capture reuses the shared scheduler/resource governor after the stopped worker is reaped. It hashes current saved inputs, rechecks them, and verifies filesystem membership/size/modification/change times under the same managed session. Delivered inputs, overflow and workspace epochs are checked before acknowledgment. Cancellation capture never starts a language worker, restores packages, publishes facts or replaces the serving generation, and can capture malformed configuration bytes. Registrations/settings and cancellation intent/baseline use the registry's stronger durability; pending cancellation survives restart. Old cancellation records migrate through capture rather than being trusted as new baselines.

The user accepted the **verified snapshot boundary** for v0.0.1. Saves absorbed during capture stay cancelled; an edit racing final verification may count as a later change and resume indexing, even if the caller's last status read was `cancelling`. This is not an atomic filesystem snapshot or exact wall-clock cutoff. Delayed events with unchanged input bytes compare equal and do not restart a compiler. Changes after the recorded baseline, including offline changes, resume through the normal update path. Explicit refresh may supersede capture; reopening a workspace does not. Resource-policy changes never clear cancellation intent.

Scan/resource/access failures retain pending intent and stale/not-ready results, report the cause, and retry through existing scheduling triggers. No failed capture acknowledges `cancelled`. Completed cancellation has a recorded fingerprint that survives restart. Per-registration identities fence stale progress/completions after removal/re-registration; a committed coherent publication still wins the cancellation race. Cursor deadlines and comprehensive query budgets remain separate work.

Resource-control capability is now **2**. SDK/control responses, managed query RPC, live publisher certification and installer target checks reject a coordinator/target lacking that contract. Worker framing remains 7 and the serving store format remains 6; there is no unrelated store/framing bump.

## Cancellation regression and correction (first-wave integration)

The frozen Debug checkpoint at source `d9b4227` failed the queued-cancellation assertion in `tests/resources.py`. A focused rerun passed all ten checks, but an unchanged-runtime bounded probe then reproduced actual unwanted resumption: five of six cancelled queued workspaces launched a compiler and published after the blocking workspace released, without any intervening source/configuration save. Delayed filesystem events can call `queue()` after cancellation; its file-event path sets force and can bypass the first-baseline guard. This is a product defect, not merely a status timing issue, and failed the R02 gate at that checkpoint. Earlier passing runs do not waive it.

Evidence: `.artifacts/qc/cd499850/result.json`, `events.jsonl`, `probe.py` and `watcher-api.json`. The same host SHA-256 was verified before/after; all probe process groups exited. Pinned notify 8.2.1 discards native event IDs and exposes no stream flush barrier. The user subsequently accepted the baseline boundary and its explicit concurrent-edit snapshot exception described above. The correction passed independent read-only review, 14 focused resource checks, both SDK compatibility checks, Rust tests, formatting and all-target Clippy. A six-workspace probe observed no compiler launches for unchanged delayed events and one publication after a post-acknowledgment save. Completed segmented Debug coverage is recorded below; neither failed full-script attempt becomes a pass.

The original failed resource fixture left a held worker because graceful shutdown drains active work. Its verified fixture group was explicitly stopped; resource-test cleanup now cancels its owned workspaces before requesting shutdown. Cleanup does not relax cancellation assertions. The expanded fixture now expects the accepted `cancelling` phase before the durable `cancelled` acknowledgment and checks no compiler launches while recording the baseline.
