## Request and result shape

- `page_size` opts a normal supported query into pagination. Use 1–1000 items per page. Existing nonpaged behavior stays available; total `limit` retains its current range/default. A capped graph's findings preserve explicit logical truncation/limit evidence. Graph traversal work limits apply once to the materialized logical result, not once per page.
- Continuations use `op:"next_page"` and an opaque `cursor`, with per-request deadline/response limits. Continuation requests cannot change the original scope, projection, page size or traversal budget. `source` and `symbol_context` may instead use the cursor for separate bounded reads through its generation.
- Each page includes its own reusable `page.cursor` and nullable `page.next_cursor`. Original `truncated`/graph limits describe logical incompleteness; more pages alone do not mean the logical query is incomplete. The last page must preserve original partial evidence.
- Tokens use a versioned private prefix bound to coordinator incarnation/cursor identity, plus a fixed-width page position. The exact spelling is private. They remain portable across clients while that incarnation lives. Restart/expiry/pressure invalidation returns `cursor_invalidated` and never switches to current data.

## File and page helpers

Saved results have a private 16 MiB encoded-file guard and 64 KiB transport chunk guard, inside the accepted shared 1 GiB pool. These are bounded implementation guards, not RAM preallocation or physical SQLite/WAL guarantees. Oversized required metadata/items fail explicitly; no evidence is silently dropped. Reserve all retained file bytes before the coordinator writes them.

Two implementers use isolated durable worktrees. Each may add only its one helper-module declaration to cursor.rs as compilation glue; all other registry/control/protocol/query/SDK edits belong to the integrator. They must not build a second query engine, add dependencies or mutate the live runtime/corpus. Focused tests precede one assembled boundary check; heavy jobs are coordinated.

### ResultStore boundary

Provide a coordinator-owned, externally serialized `ResultStore` with `open(directory)`, `begin(key, expected_bytes)`, `append(key, offset, bytes) -> next_offset`, `complete(key, sha256) -> StoredResult`, `get(key) -> StoredResult`, `remove(key)` and `reset()`. `StoredResult` exposes path, bytes and SHA-256. Keys are exactly 32 lowercase hexadecimal characters, generated by the integrator from cursor identity; arbitrary paths are never accepted. `append` is bounded by MAX_RESULT_CHUNK and expected total size, rejects reordered/conflicting data and never overwrites a completed file. `complete` requires exact length/hash and atomically makes the file readable. No per-chunk fsync is needed: restart invalidates all cursors.

Use private files/directories and reject symlinks/nonregular entries. Cleanup is idempotent for absent owned files, preserves errors and must not delete unrelated files or indexes. Incomplete uploads and restart cleanup are explicit. Registry integration removes files before releasing their quota reservation; failed cleanup remains charged. An already-open read descriptor stays coherent across unlink. This module supplies no independent quota pool; its caller already reserved capacity and holds the coordinator fence.

### Page helper boundary

Use crate-local `encode(result: serde_json::Value, options: EncodeOptions, execution: Execution) -> Vec<u8>` and `read(reader: impl Read+Seek, options: ReadOptions, execution: Execution) -> serde_json::Value`, returning the common Result type. EncodeOptions contains op, total_limit, page_size, cursor_prefix, response_max_bytes. ReadOptions contains page position, cursor_prefix, expected_generation, response_max_bytes, freshness and optional coordination status. Match existing Rust ownership/types pragmatically; report any necessary signature change before editing shared call sites.

The input is the bounded result from existing Rust operators. Encode it once into a versioned indexed file with frozen page partitions. Reuse the shared complete-response encoder/budget and include token/envelope/metadata bytes while packing. Preserve all required coverage/provenance/uncertainty. Symbols, occurrences, contexts and explicit coverage pages have their own primary array; graph findings and boundaries are whole atomic items with explicit section totals so omitted later boundaries cannot be mistaken for absence. Never split a supporting path, declaration context or individual item.

Store shared headers once and read only needed indexed page data, rather than parse/copy the whole graph on every page or duplicate large headers per item. Successful replay returns identical indexed items/order/next position. A different response cap may reject a frozen page but cannot repack it. Only freshness/coordination may vary, and all resulting bytes still count. Invalid/truncated/version-mismatched data or generation mismatch invalidates the cursor rather than falling back to disk/current data. Check the common deadline during encoding, page selection/reads and JSON work. Bounded empty results still yield one valid replayable cursor page.

## Integrator obligations

The coordinator owns files, quotas, leases and immutable query scope; the consumer's Rust core executes queries and reads pages/source locally. Bounded chunks use the versioned local control codec. Add an explicit cursor capability/version check; older peers fail actionably. Do not advertise cursor support until wired. SDK/native query contracts must reject mismatches consistently.

Coordinator incarnation is independent of optional live freshness. Startup invalidates prior pins across managed indexes and cleans old result files before accepting new pagination. Periodic cleanup and failed/abandoned upload leases reclaim retained state. Index publication previews/evicts through the registry under an admission gate, waits outside the serving write transaction and preserves current/stale views while reads finish. Snapshot source/context readers use the same original generation and the remaining overall deadline.

Required assembled checks include actual multiple-process replay across saved publication, source/context matching, terminal partial flags, expiry/restart invalidation, quota/count pressure with active reads, streamed upload failure/cleanup, old-peer errors and matching CLI/MCP/Node/.NET behavior. ## Assembled API and ownership

The coordinator service now owns the shared registry, result files, startup cleanup, periodic expiry and publication gate. CLI/MCP and both native bindings use the common Rust client to execute and read locally. Native query contract 2 and cursor-control capability 1 are explicit compatibility checks; ABI 1, worker/control protocol 7 and base store 6 are unchanged. Optional live freshness is independent of the cursor owner.

Start with `{"op":"symbols","limit":100,"page_size":10}`. Each result contains `page.cursor`, nullable `page.next_cursor`, position/page count, the total limit/page size and per-section totals/start/count. Read/replay with `{"op":"next_page","cursor":"TOKEN"}`; only `deadline_ms` and `response_max_bytes` may be added. Changing scope on continuation fails explicitly. Node uses its ordinary query API. .NET also provides `Index.NextPageAsync` and `Workspace.NextPageAsync`, which emit the sparse continuation shape. Source/context accept the token separately and preserve the pinned generation. Continuations do not wait for a newer generation: they read their immutable snapshot immediately and report freshness against current coordinator status.

`know-code cursors` reads the shared personal policy and pending cleanup/pressure warnings; `--max-count COUNT` and `--retention-bytes BYTES` change it centrally. Defaults remain 128 cursors and one logical 1 GiB pool. Settings persist independently of workspace analysis settings. Busy quota reductions remain pending and periodic cleanup enforces them when readers finish. No active reader is evicted to force an immediate reduction.

Startup activates a new owner before pagination. Failed old-pin cleanup is queued fairly, remains visible and blocks new cursor admissions while unknown retained bytes exist. Unregister marks that workspace's tokens retiring before registration removal; re-registering the same path cannot revive them. File deletion precedes pin/reservation release on expiry, abandonment, pressure or explicit invalidation. Failed deletion stays charged and is retried. Shutdown drains publication and staging cleanup before releasing the writer fence.

No final full/optimized, physical disk/WAL ceiling, whole-query peak-memory bound, external publication or live installation change is implied.
