# KnowCode 0.3 plan

October 22, 2026. Two to three weeks of work.

0.3 makes KnowCode keep up with a real workspace of hundreds of repositories on its own, and measures what agents
actually spend when they re-check an answer. 0.2 shipped answers as accurate as plain tools, used unprompted in every
session of its [public study](../../eval/public-v1/results.md), at about the same token cost. It missed its re-check
criterion: agents still re-check about half of KnowCode's answers. Most of those re-checks read the code around a
cited line, or check a clean answer anyway, and most of them confirm it. Repeated runs of one build also moved the
re-check rate by about 0.2, so a study of 24 questions can't separate a real change from noise.

A large private workspace showed the other gap. Of about 500 repositories under one workspace root, only about 150
had been indexed: repositories are indexed lazily, one at a time, and a new one goes unnoticed until something touches
it. Workspace answers left the rest out without saying so.

## Gate

0.3 ships when a new public study has been run and published, with every failure and loss reported. Its criteria are
fixed, and published in its protocol, before any 0.3 change is measured. No comparative or benefit claim appears
before that.

**Proposed criteria** (fixed at pre-registration):

1. **Re-check cost halved.** Tokens agents spend re-checking KnowCode answers, per session, at most half of 0.2.0's
   on the same questions. This replaces 0.2's re-check rate. A re-check that confirms a clean answer costs tokens; the
   study measures that cost, not the habit.
2. **Re-checks that change the answer** are reported per run (descriptive). A re-check that finds something KnowCode
   missed is a KnowCode failure and is listed as one.
3. **Answer F1 and recall at least equal** to the plain-tools arm.
4. **Research tokens at most equal** to the plain-tools arm, schemas included.
5. **Unprompted use** in at least 20 of 24 sessions where the prompt doesn't name KnowCode.

**Workspace gate** (product, not the study): on a public workspace of at least 100 repositories, every repository is
indexed and current without an `index` command, a repository added under a root is noticed and indexed, and answers
never leave a repository out without saying so. Measured on a quiet machine, with indexing time reported by phase.

## Order

Measure before changing. Week 1 pre-registers the new study and runs its baseline on 0.2.0, and measures where
indexing time goes. Weeks 1–2 build the changes. Week 3 runs the study on the release candidate, publishes, and
releases.

### 1. Workspace at scale

- **Measure first:** time and instruction counts per indexing phase (discovery, parse, write, text content, derived
  data) on small, medium and large public repositories, on a quiet machine. Defaults are set from this.
- **New and removed repositories** ([#40](https://github.com/bubstackdev/knowcode/issues/40)): roots are checked
  cheaply when `serve` starts and as queries arrive. A new repository's privacy file is read before anything else,
  then it is queued for background indexing. Until it is indexed, workspace answers say "N repositories found, not
  yet indexed" in `incomplete`; `kc_status` lists them.
- **Adaptive throughput** ([#41](https://github.com/bubstackdev/knowcode/issues/41)): read the machine's cores,
  memory and power state; index several repositories at once under a CPU and a memory budget; let an explicit `index`
  use most of the machine; scale background indexing up only when the machine is idle and on power, and back off
  under load, on battery or under memory pressure. Queries always come before indexing.
- **Measured by** the workspace gate, with time per phase before and after.

### 2. A study that measures the cost

- **A new bank, public-v2:** fresh questions sampled the same way as
  [public-v1](../../eval/public-v1/sampling.md), from the same and new public repositories. public-v1 has been run
  five times, and 0.2's fixes were tuned against questions near it.
- **Enough runs to see an effect:** each build is run twice on the bank in a fixed order, or the bank grows until a
  repeated run of one build moves the criteria less than the effect we look for. The size is chosen from a pilot,
  before the baseline.
- **Re-check cost:** count the tokens of every call that re-checks a KnowCode answer (the 0.2 detector decides which
  calls those are), and whether each one changed the final answer.
- **Harness fixes, frozen before the baseline:** compound shell commands (`cd x && grep …`), refused today in every
  arm, are allowed or rewritten the same way in every arm; labels say which calls are optional rather than counting
  calls they can't rule out as false positives.

### 3. Cheaper to trust

0.2's diagnosis found agents read the source around a cited line, or check a clean answer anyway.

- **The statement, not just the line:** where an answer cites a line inside a larger statement or call, it carries
  the statement. 0.2's search change cut these re-checks from 13 to 2 in one arm; extend it to `kc_refs`,
  `kc_context` callers and `kc_impact` steps.
- **Win back size:** `kc_search` answers grew about 16% in 0.2 by showing every hit up to 60. Keep that only where it
  saves a later search, measured on the study's calls.
- **Measured by** criterion 1 and research tokens.

### 4. Linking precision

- **Client calls go to the server they call:** an untagged client's operation call links only to actions in the
  server repositories that client calls, not to same-named actions anywhere in the workspace.
- **Microsoft DI descriptors:** `services.Add(new ServiceDescriptor(…))` and its relatives are read as registrations.
- **Measured by** the bank's HTTP and DI questions, and the accuracy bank.

### 5. Tech debt

0.2 already did what its plan listed here: the per-query context (`limits::Operation`), the `unsupported` table
([#14](https://github.com/bubstackdev/knowcode/pull/14)) and one graph for the walks
([#21](https://github.com/bubstackdev/knowcode/pull/21)). What's left of each:

- **Per-query state still kept per thread:** the summaries an answer read from cache and the indexes it used, and
  `kc_search`'s worker threads, which didn't run as the call (a cancelled call didn't stop them).
- **Unplaceable HTTP registrations** are still route rows marked unsupported; they move to the `unsupported` table.
- **A second walker:** `coupled`'s static link still uses the old in-repo tracer; it moves to the shared graph and
  the old walker goes.

## Not in 0.3

- Windows.
- Questions the bank shows KnowCode losing today (co-change and history lookups).
- Paused feature targets.

## Release

- **Per pull request:** the usual gates.
- **Clean-machine acceptance:** the script on Linux and macOS, including unprompted sessions.
- **Updates:** a cross-version update from 0.2.0.
- **Evaluation:** the published study is linked from the README and the release notes.
