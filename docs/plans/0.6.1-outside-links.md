# 0.6.1: outside labels linked

Moved past 0.6.1, which shipped review fixes only; this work carries to the next release.

0.6 ships with one condition of its identity gate missed: "no link to an indexed declaration where the toolchain
resolves outside the workspace" ([identity-v1](../../eval/identity-v1/README.md)). This page lists every outside
label still linked, by cause, with the fix for each, how many it fixes and what it risks. These links are 0.6.1's first
item.

## Where it stands

The figures come from identity-v1 on integration/0.6 at 82997ab with #199 merged (the tree 0.6 ships). The fixes
kc-overlay has open for C# are expected to take C# from 11 to 6.

| Language | Outside labels | Linked `unique_name` | Linked `exact` | `exact` precision |
| --- | ---: | ---: | ---: | ---: |
| C# | 646 | 6 | 5 | 0.986 |
| Swift | 471 | 20 | 3 | 0.992 |
| TypeScript | 359 | 37 | 0 | 0.998 |

71 outside labels are linked, 63 of them `unique_name`. The rest of the outside labels KnowCode leaves unresolved or
lists as candidates. Of the 8 `exact`, 5 are C# extension methods, or calls an instance member or a static framework
member takes (cause B), and the 3 Swift ones are causes E and H.

## Causes

### A. A member through a receiver whose type KnowCode doesn't know, linked to the repo's one member of that name (46)

The receiver's type isn't known, and the repo declares exactly one member of the name, so KnowCode links it
(`unique_name`). The toolchain binds a library's member.

- **TypeScript, receivers rooted in a package import (26):** jellyfin-web calls the SDK as
  `getLibraryApi(api).getItems(…)`. `getLibraryApi` is imported from `@jellyfin/sdk`, and KnowCode links `getItems` to
  `src/apiclient.d.ts`, a declaration file for the legacy client. The same goes for `getSessions`, `deleteUser`,
  `updateNamedConfiguration`, `getStudios`, `getLiveTvChannels`, `cancelTimer`, and `Items` on an SDK result.
- **TypeScript, locals of a package type (7):** `result.success` on a zod parse result, `query.isError` on a
  react-query result, `box.left` on a `DOMRect`, and `TotalRecordCount`, `Status` and `OfficialRatings` on SDK models.
- **Swift (11):** `str.endIndex`, `items.startIndex`, `range.lowerBound` and `.upperBound`, `.size`, `Element.allCases`
  and `container.decodeIfPresent`. The receivers' types aren't tracked; the toolchain binds the standard library's.
- **C# (2):** `prop.GetMethod` (PropertyInfo's), `Request.QueryString` (ASP.NET's HttpRequest).

**Fixes:**

- **A1 (TypeScript):** a receiver rooted in a value imported from a package (a bare module specifier: the call
  `getLibraryApi(api)`, a member chain on it, an `await` of it) is outside: `external_likely`, not linked, unless the
  repo augments that module (`declare module '…'`). This fixes about 26. Recall risk: low. A repo declaration is
  reached through a package's value only by module augmentation, which stays linked.
- **A2 (all three):** with an unknown receiver, a name the standard library declares as an instance member is
  `external_likely`. KnowCode already does this for the names in its lists (`STDLIB_MEMBERS`, `DOTNET_MEMBERS`,
  `JS_MEMBERS`). Add the ones these labels show: `startIndex`, `endIndex`, `lowerBound`, `upperBound`, `allCases`,
  `decodeIfPresent` (Swift); `GetMethod`, `QueryString` (C#); `success`, `isError`, `left` (TypeScript). This fixes
  about 16 (11 Swift, 2 C#, 3 TypeScript). Recall risk: moderate. A repo member of one of these names, reached through
  an untyped receiver, stops being linked. Measure it on identity-v1 (recall linked must not drop more than 0.005 in
  any language) and the replay gate before merging.
- **The rest (4: `TotalRecordCount`, `Status`, `OfficialRatings` and one `Items`):** these need the local's type
  (`const { data } = useQuery(…)`). They're left for receiver typing through package types.

### B. A C# extension method whose `this` type doesn't fit the receiver (9)

`items.FirstOrDefault()` on an `IQueryable`, an array or an `IEnumerable` links to jellyfin's
`ReadOnlyListExtension.FirstOrDefault(this IReadOnlyList<T>)`. `list.AddRange(…)` links to an extension where
`List<T>.AddRange` (an instance method) wins. `hashString.IndexOf(…)` on a `ReadOnlySpan` links to the
`IReadOnlyList` extension. `lan.Split(…)` on a `string` links to a repo `Split` extension, and `Expression.Not(…)` (the
framework's static method) to a repo extension class's `Not`. There are 4 `FirstOrDefault`, plus `AddRange`,
`IndexOf`, `Split`, `Not` and `Count`.

**Fix:** an instance member of the receiver's own type beats an extension method, as C# decides. An extension method
applies only when its `this` type is the receiver's type, one of its supertypes or interfaces, or a type parameter
those satisfy. With a receiver typed outside the repo whose interfaces aren't known, an extension on a different
repo-visible interface is a candidate, not `exact`. This fixes about 9; kc-overlay's open fixes cover 5 of them. Recall
risk: low with a known receiver. With an unknown receiver nothing changes.

### C. A bare TypeScript import placed by file name (3)

`import { createHash } from 'crypto'` in hono's tests links `createHash` to `src/utils/crypto.ts`. The import is
Node's `crypto`, and no tsconfig path maps it to the repo. KnowCode marks it `filename_guess`.

**Fix:** a bare specifier never resolves to a repo file by its name. It resolves only through tsconfig `paths` or
`baseUrl`, a workspace package's name, or a relative path. Otherwise it's outside. This fixes 3. Recall risk: low,
since a bare specifier naming a repo file needs `paths` or `baseUrl` to compile at all.

### D. A global TypeScript type shadowed by a repo type the file doesn't import (1)

`Response` in hono's `fetch-result-please.ts` is the platform's, but it links to `Response` in `src/types.ts`, which
that file doesn't import.

**Fix:** an unqualified TypeScript type resolves to a repo declaration only in its own file or through an import (or a
global declaration file). Otherwise it's the library's. This fixes 1. Recall risk: low.

### E. A Swift type of the same name from an imported package (3)

`FileDescriptor` in `_NIOFileSystem` is swift-system's (`SystemPackage`), and `descriptor.close()` is its `close`.
KnowCode links both to NIOCore's `FileDescriptor` protocol.

**Fix:** a type name resolves to the repo's declaration only when the file sees its module. If the file imports a
package module that declares the name and doesn't import the repo's module that declares it, the package's wins.
Swift's import list is already read. This fixes 3. Recall risk: low to moderate, and needs the packages' declared
types, which the dependency manifest names but KnowCode doesn't read.

### F. A Swift async overload against a synchronous library function (3)

`XCTAssertThrowsError(…)` and `XCTAssertNoThrow(…)` in swift-nio's tests link to the repo's `async` overloads in
`XCTest+AsyncAwait.swift`. The calls aren't awaited, so the toolchain binds XCTest's.

**Fix:** record `await` at a call site. A call that isn't awaited never links to an `async` declaration, and an awaited
call prefers one. This fixes 3, and the last wrong-`exact` cause H of the Swift breakdown (`getOption`). Recall risk:
low.

### G. A Swift wrapper declared for another platform (2)

`ioctl` and `unlink` link to swift-argument-parser's and swift-nio's own functions, declared in an `#if os(Windows)`
branch. On Linux the toolchain binds Glibc's.

**Fix:** a free function declared only inside a branch for another platform (`#if os(…)`, `#if canImport(…)`) is a
candidate, never `unique_name`, when the platform library also declares the name. This fixes 2. Recall risk: low; it
needs the enclosing `#if` condition recorded on declarations.

### H. A Swift member reached through an outside protocol or overloaded on argument types (4)

- `decoder.singleValueContainer()` on a `Decoder` links to a repo conformer's member (`MinimalDecoder`).
- `buffer.append(contentsOf:)` on a swift-collections `Deque` (2) links to an extension a test target declares.
- `JSONDecoder().decode(_:from: Data)` links to the repo's `decode(_:from: ByteBuffer)` extension.

**Fixes:**

- A receiver typed as an outside protocol never links to one conformer's member.
- An extension declared in a test target is seen only from that target.
- A repo extension on an outside type whose parameter types differ from the arguments is a candidate.

Together these fix 4. Recall risk: low.
