# KnowCode 0.8 plan

October 29, 2026. About six weeks of work, starting together with 0.7 and releasing after it.

KnowCode is open source and local-first. It aims to cover about 95% of what the large code-intelligence products
offer, with a local equivalent wherever they host a feature. Every feature counts only once a gate with no model call
passes. 0.8 takes on review, which hosted products run as a service on every pull request. The local equivalent is
built in three parts:

- **One bounded `review` answer for a diff**, printed as markdown, JSON or SARIF. It includes contract changes that
  break other repos, and a walkthrough with diagrams that the user's own agent can turn into prose.
- **Read-only rules and monitors**, which check code patterns.
- **A separate public repository**, `bubstackdev/knowcode-ci`. It holds a GitHub Action and a GitLab template that
  run `knowcode review` on the user's own runner and post the result.

KnowCode only prints. It never posts, holds no credentials and writes nothing into a repo. 0.8 also finishes and
publishes compare-v1, the answers-only comparison with codebase-memory-mcp and Serena that 0.7 starts.

What 0.7 and earlier leave open for review:

- **Review context takes several calls.** A client reviewing a change joins `impact --diff`, `tests`, `context` and
  `coupled` itself. Each call has its own continuation, and nothing says which consequences of the change the client
  hasn't looked at.
- **Breaking changes across repos aren't flagged.** KnowCode links HTTP routes, bus messages and SQL tables across
  repos. A diff that removes a route, renames a message field or drops a column changes those links, but no answer
  says which consumers the change breaks.
- **No checks of the team's own patterns.** `grep_ast` matches one pattern at a time when asked. There is no rule
  file a repo can keep, and no way to ask "what's new since main".
- **No diagrams.** `path`, `flow` and `areas` answer as text and trees only.
- **Nothing runs in CI.** Restricted mode was made for automated pipelines, but there is no ready workflow for one.
- **`task` walks twice.** Its tests section runs `tests`, which builds a symbol graph and repeats the depth-1 `impact`
  walk that the dependents section has just done on the same files (`crates/knowcode/src/task.rs`, `ops::tests` in
  `crates/knowcode/src/ops.rs`). `review` would repeat it a third time.
- **compare-v1 is partial.** 0.7 publishes references and impact only.
- **0.7's gate misses**, if there are any, stay with 0.7.x and are not 0.8's work.

## Gate

0.8 ships when these pass, and they are published with the release as `eval/release-gate/0.8.0.md` (new file). They
are compared with the latest 0.7.x. The figures for 0.6.1, the release before the two that run in parallel, are shown
beside them, so that a regression carried through 0.7 is visible. None makes a model call. Labels come from git, a
compiler or a reference tool run directly, always on public repositories, and never from KnowCode or a model.

- **Tool cost per turn** for each profile:
  - The default `one` profile may grow only by the new op names and the `format` choice, stated in tokens and
    justified in the release notes.
  - `all` lists the new tools, which aren't loaded up front.
  - Capabilities stay served on request.
- **Replay and history gates** as in 0.7: no regression beyond tolerance under either scorer.
- **Identity:** identity-v1 and v2 hold what 0.7 shipped: `exact` at least 0.99 in every language, and no outside
  label linked.
- **Review answers (review-v1, new):**
  - **The set:** public commits that a later fix repaired, found from git alone. A fix's changed or deleted lines
    are traced back with `git blame` to the commit that introduced them, within 90 days. The commits are drawn per
    language with a recorded seed, over tasks-v1's repositories and the Go and JVM repositories added in 0.7.
  - **Labels:** the files and tests the later fix changed.
  - **The test:** `review --diff` against the introducing commit, scored by recall within a byte budget against
    `impact --diff` alone. The review answer must be higher at equal or smaller median answer bytes, with paired
    differences and counts reported.
  - The set's README is committed before KnowCode's answers on it are read.
- **Contract changes (contract-v1, new):**
  - **The set:** public commits that remove or change an HTTP route (its path, verb or request contract), a bus
    message's fields, or a table's columns. They come from public repositories whose consumers are in other public
    repositories, with the public-v1 subjects as candidates (Jellyfin server and web client, Bitwarden server and
    clients).
  - **Labels:** consumers are labelled by a script that reads both sides at the pinned commits, using the route sets
    labelled in 0.7 and the toolchains' references, never KnowCode.
  - **The test:** the precision of the consumers `review` reports as broken is at least 0.95, and recall is
    reported.
- **Rules:** for every rule in the fixture set, `knowcode rules` returns the same matches as the `ast-grep` command
  line run directly on the same files, at the version that matches the embedded ast-grep-core 0.50. The matches are
  (file, start, end) sets, and they must be equal. The reference runs in the container.
- **Monitors:** monitors are replayed over the history of at least three public repositories, and they must fire on
  exactly the commits that are labelled.
  - A monitor with a text pattern is labelled with `git log -G`.
  - A structural monitor is labelled by `ast-grep` run at each commit and at its parent, counting new matches.
- **Walkthrough and diagrams:**
  - The walkthrough has golden files, and every row's `file:line` exists at the head commit.
  - Mermaid output for `review`, `path`, `flow` and `areas` is checked against golden files, and parsing its edges
    back gives exactly the answer's edges.
- **SARIF:** every SARIF output validates against the SARIF 2.1.0 schema, checked with a pinned copy in the
  container. GitHub code scanning accepts it in the end-to-end run.
- **Privacy and writes:**
  - A diff that touches content a repo's privacy file blocks gets `withheld`, never the content, in every format.
  - SARIF and markdown carry locations and messages, never source lines from blocked files.
  - After `review`, `rules` and monitors, the repo's tree and its git state are unchanged.
- **The CI repository:**
  - The action passes the contract gate's restricted-mode check inside its job, bound to the checked-out repo, with
    only the review ops allowed.
  - Both the GitHub Action and the GitLab template run end to end on a public fork, and post their findings on a
    test pull request or merge request.
- **compare-v1, finished** (W5): see W5's check below. It doesn't change any gate item.
- **Task and review walk (perf #7):** the 54 tasks of [tasks-v1](../../eval/tasks-v1/README.md) give byte-identical
  answers to 0.7.x's, with instructions retired and symbol graphs built reported. `task` and `review` each build one
  graph and one depth-1 walk per call.
- **Contract gate:** the capabilities entries for `review` and `rules`, and the new `format` parameter, match what
  the server accepts and returns.
- **Task answers, worktrees, workspace gate, clean-machine acceptance with restricted mode, an update from 0.7.x, and
  the binary size:** as in 0.7. The new ops have snapshot files of their own. `walks.txt` is unchanged, except for
  the answer-evidence candidate's single reviewed bless commit (W3).

No comparative or benefit claim about agents follows from the gate.

**Feature rows this release closes:**

- review context for a PR;
- running in CI and commenting on the PR;
- custom review rules;
- the PR walkthrough;
- code monitors;
- breaking changes across repos;
- diagrams.

The gate page lists each row with its gate result.

## Branching and shared files

The branching is 0.7's: `integration/0.8` is cut from v0.6.1 and merges `integration/0.7` once a week, then 0.7's
release commit. It never rebases, and nothing is force-pushed.

After each weekly merge, the lead does four things:

- checks `CHANGELOG.md`'s headings, since a release merge has folded entries under the wrong heading before;
- renumbers schema versions if needed;
- measures the dist binary again;
- runs `scripts/check-docs.py`.

| File | Rule in 0.8 |
| --- | --- |
| `crates/knowcode/src/ops.rs` | New ops live in their own modules (`review.rs`, `rules.rs`, `diagram.rs`). `ops.rs` gets one dispatch line per op, added in that op's last PR. **Two exceptions, each its own lead-reviewed PR (W3):** perf #7's split of `ops::tests`, and the answer-evidence candidate's route lines. |
| `mcp.rs`, `help.rs`, `capabilities.rs`, `main.rs` | Op rows and help topics are appended in one PR per op, at the end of each workstream. The lead squashes them in a fixed order, W3 then W4, and `scripts/check-docs.py` runs after each squash. |
| `crates/knowcode/src/render.rs` | W4 adds a call to `diagram.rs` and the markdown and SARIF formats. W3 doesn't edit it. |
| `crates/kc-index/src/http.rs`, `bus.rs`, `sql.rs` | Not edited. Contract changes read the links through the store's query API. |
| `Cargo.toml`, `Cargo.lock` | 0.8 adds no grammar. Any new crate goes through the lead. |
| `size-budget.txt` | Raised only in the commit that grows the binary, citing its dist build. It is measured again after each merge from `integration/0.7`. |
| Schema version | W3 and W4 take the two numbers after 0.7's. |
| `docs/usage.md`, `docs/configuration.md` | 0.8 edits these, for the new commands, flags and the `rules` config keys. It doesn't edit `docs/languages.md`. |
| `CHANGELOG.md` | `integration/0.8` has its own `## Unreleased` section, and each workstream appends to it only. |
| `eval/queries.toml` | 0.8 appends a review section. |

## Work

Three workstreams, each with one agent: W3, W4 and W5's second half. W5 also picks up overflow from W3 or W4.

### W3: review, contract changes and the walkthrough (about 7 agent-weeks)

The roadmap's 5.5 agent-weeks, plus perf #7 (about half a week) and the answer-evidence candidate (about one week).
One agent can't fit 7 into the release, so W5 takes the walkthrough once compare-v1 is published.

**Touches:**

- `review.rs` in the knowcode crate (new file), modelled on `crates/knowcode/src/task.rs`;
- perf #7: `crates/knowcode/src/task.rs`, `crates/knowcode/src/tree.rs` and the body of `ops::tests`;
- `contracts.rs` in kc-index (new file), which reads the HTTP, bus and SQL links through the store's query API;
- `crates/kc-index/src/diff.rs`, for the changed ranges and the removed definitions it already finds;
- the review gate and its labeller in scripts/eval (new files, standard library only, with tests);
- `eval/review-v1/` and `eval/contract-v1/` (new).

**Order:**

1. **The review-v1 set, labels and scorer**, with the `impact --diff` baseline measured on the 0.7 build before any
   review code exists.
2. **Perf #7, in week 1, in its own lead-reviewed PR.**
   - `task` builds one symbol graph and one depth-1 walk for its files.
   - The dependents section and the tests section both read that walk, and each keeps its own evidence filter.
   - `ops::tests` is split so that test selection can take a walk it is given. `review` reads the same shared walk.
   - **Check:** `walks.txt` unchanged, and the tasks-v1 answers byte-identical, with the counts reported.
3. **Freeze the `review` answer structure by the end of week 1.** W4 builds markdown, SARIF and diagrams on it. The
   answer has these sections:
   - what the diff changes, by symbol;
   - what depends on it, in this repo and across repos;
   - the contracts it changes, with their consumers;
   - the tests to run, which are advice and never the only tests;
   - the files that usually change with it but weren't changed;
   - the questions the index can't settle.

   Each section carries its own completeness and continuation, as `task`'s do.
4. **The bounded `review` op**, from the CLI (`knowcode review --diff <base>`) and as an op of the `kc` tool.
5. **Contract changes.** A removed or changed route, a message field, or a table column, each with the consumers in
   other repos that the link reaches. A consumer reached only through a `unique_name` or ambiguous link is listed as
   possible, never as broken.
6. **The walkthrough:** changed areas, entry points reached, a Mermaid sequence of the main path, and a recipe that
   tells the user's agent how to write the prose from it. KnowCode writes no prose of its own.
7. **Docs and help:** `docs/usage.md`, the help topic and capabilities, all in one PR at the end.

**Candidate: answer evidence (about 1 agent-week, after step 4).** A review lists who calls a changed symbol, and the
client then needs every line where each caller makes that call. Today a dependent names one site, so the client greps
for the rest. Work begun before 0.6 and never merged (saved from the closed `kc-evidence-shelved` branch) added four
things:

- every call line per caller (`at line 526 (also 532, 592)`, and `also` in JSON);
- the lines an action's route is written on, in `impact` and `context`: its own attribute, then the prefix on its
  controller or a base;
- for a type's context, which lists are whole or cut, and what was searched for the whole ones;
- answers of 20 rows or fewer quote every cite.

That work was based on a tree from about 70 commits before 0.6.0, so it is **rewritten against 0.6's answer
contract** (its completeness fields, cite checks and walk graph), not ported. Only the per-caller lines are needed for
`review`. The other three are taken only if they pass the same checks.

- **Touches:** `crates/kc-store/src/trace.rs`, `crates/knowcode/src/walk.rs`, `crates/knowcode/src/tree.rs` and
  `crates/knowcode/src/cite.rs`, plus one text line in `crates/knowcode/src/render.rs`, agreed with W4. Route lines
  touch the route rows in `crates/kc-store/src/query.rs` and their use in `ops.rs`. That `ops.rs` hunk is an accepted
  exception to the dispatch-line rule, and goes in its own PR, reviewed by the lead.
- **Check:**
  - On identity-v1 and v2, for each caller a dependent names, its `also` lines plus its site equal the reference
    sites the toolchain labels in that caller for that target. Precision and recall are reported, and every
    difference is listed.
  - Replay answer bytes grow by an amount stated per tool, measured on this build. No figure is carried over from
    the old branch.
  - Walks change, so `walks.txt` is regenerated in one bless PR of its own, reviewed by the lead. That is 0.8's
    only change to it. Its diff must show only added `also` lines. Otherwise the work is split, or moved to 0.9.
- **If it doesn't fit in the five weeks,** `review` names one site per caller and says so, and the work moves to
  0.9.

**Check:** on review-v1, the review answer is higher than `impact --diff` at equal or smaller median bytes.
contract-v1 reaches at least 0.95. The walkthrough's golden files pass, with every `file:line` existing.

### W4: rules, monitors, diagrams, output formats and the CI repository (about 5.5 agent-weeks)

**Touches:**

- `crates/kc-index/src/structural.rs`, for rules over ast-grep-core, and `rules.rs` in the knowcode crate (new file);
- `diagram.rs` in the knowcode crate (new file), for Mermaid, called from `crates/knowcode/src/render.rs`;
- `sarif.rs` in the knowcode crate (new file), and the markdown renderer of `review`;
- the rules and monitors fixtures;
- `bubstackdev/knowcode-ci`, which the user creates and W4 sends PRs to: `action.yml`, the GitLab template, and an
  end-to-end workflow on a public fork.

**Order:**

1. **The rules format and loader.**
   - Rules are ast-grep's rule YAML, a subset limited to what ast-grep-core supports. `fix` is refused, because
     0.8's rules only report.
   - Rules are read from paths given on the command line or in config (a new `rules` key, documented in
     `docs/configuration.md`). A rule file the user commits to their repo is read, never written.
2. **Monitors.** A monitor is a rule run with a base (`--new-since <ref>`). It reports only the matches the base
   didn't have. Its state is the base ref, so nothing is stored. It runs when asked, from the CLI, the op or CI. There
   is no daemon and no notification.
3. **Mermaid** for `path`, `flow` and `areas`, through a `format` choice. Every edge the diagram shows carries its
   confidence. Ambiguous edges are drawn dashed.
4. **Markdown and SARIF rendering of `review`**, on W3's frozen structure.
   - SARIF results carry locations, rule ids and messages, but no source snippets.
   - Contract breaks are errors, and possible breaks are warnings.
5. **The CI repository:**
   - The action installs a pinned KnowCode release and checks its attestation.
   - It runs `knowcode serve --restricted`, bound to the checkout, or the CLI under the same scope. It caches the
     index with the runner's cache, and posts markdown as a comment and SARIF to code scanning.
   - The GitLab template does the same, with a merge request note and a code quality report.
   - Versions follow KnowCode's: a `v0.8.0` tag, plus a moving `v0` tag that users write as `@v0`.
   - Moving `v0` is a narrow exception to the no-force-push rule. It applies only to that one tag in that one
     repository, and only the repository's release workflow moves it.
6. **Docs.**

**Check:**

- rule results equal `ast-grep`'s;
- monitors fire on exactly the labelled commits;
- diagram edges equal the answer's edges;
- SARIF validates;
- the action passes the restricted-mode check, and both CI templates pass their end-to-end runs on a public fork.

### W5: compare-v1, finished and published (about 2 of its 4 agent-weeks)

**Touches:** the same files as in 0.7: the compare scripts in scripts/eval, and `eval/compare-v1/`.

**Order:**

1. **Extend to the whole mapping** committed in 0.7:
   - questions: references, callers, impact, find, locate and task;
   - languages: C#, TypeScript, Swift, Go, Java and Kotlin, where a set has labels.

   Nothing is remapped after a run. A change to the mapping makes a new version, compare-v2.
2. **Re-run** on the 0.8 release candidate, with the tool versions pinned in 0.7, then once more with each tool's
   latest release, each pinned by digest. Both are published, so that a tool's own improvement isn't hidden.
3. **Run twice and check that the scores are identical,** then **publish** `eval/compare-v1/results.md` with every
   miss, KnowCode's included, and the "no counterpart" rows. Link it from `docs/evaluation.md`.
4. **Then take W3's walkthrough** (its step 6), and any W4 overflow after that.

**Check:**

- two runs give identical scores;
- the mapping's commit predates the first run;
- third-party code ran only in the container;
- every miss is published;
- the wording claims nothing beyond the published figures.

## Risks

- **`review` may not beat `impact --diff` on review-v1.** If it doesn't, the sections that don't add recall per byte
  are cut. A failed condition ships only by the user's decision, with the miss stated, as 0.6's identity miss was.
- **contract-v1 may have few cases.** Public commits that break a consumer in another public repository are rare.
  If fewer than 30 are found, the set grows to more pairs of public repositories before anything is scored, never
  after.
- **The structure freeze in week 1.** W4 depends on it. If it has to change later, W4's renderers change with it in
  the same PR.
- **ast-grep's version against ast-grep-core 0.50.** The reference command line must match the embedded core. A
  rule feature the core lacks is refused and stated in the rule's error, never ignored.
- **Tool cost.** Two new ops and a `format` parameter grow the default tool's schema a little. The growth is measured
  and stated.
- **The CI repository depends on the user creating it.** Until it exists, W4 builds the action in a scratch
  repository and moves it over by PR.
- **The moving `v0` tag** is the one force-update allowed: only `v0`, only in knowcode-ci, only by its release
  workflow. A hand-moved tag is a defect.
- **W3 is the longest workstream** at about 7 agent-weeks. W5 takes the walkthrough. If the evidence candidate's
  bless diff isn't clean, the candidate moves to 0.9 and the release keeps its date.
- **Weekly merges from 0.7** bring in its schema, grammars and size growth. Each merge is followed by the size check
  and `check-docs.py` before anything else is squashed.
- **The answer-evidence rewrite** reaches the walk graph and the cites, which every walk shares. If its bless diff
  shows more than added `also` lines, it is split or moved to 0.9.
- **compare-v1 on a tool's latest release may differ from the pinned one.** Both are published, and only the pinned
  run is compared across releases.

## Not in 0.8

- Posting from KnowCode itself. The CI repository posts, and KnowCode only prints.
- Review prose or fixes written by a model. The user's agent writes these from KnowCode's facts.
- Rules with `fix`, and printed patches (0.10).
- Rules mined from git history (1.0).
- A wiki or graph view (0.12).
- gRPC, GraphQL and tRPC contract changes (1.0).
- Monitors as a background service or a notifier.
- A paid agent study.

## Release

- **Per pull request:** the usual gates, plus the replay subset.
- **Clean-machine acceptance** on Linux and macOS, including restricted mode and a `review` of a public commit.
- **Updates:** an update from 0.7.x.
- **The CI repository** is tagged `v0.8.0` after KnowCode's 0.8.0 release, pinned to its assets. Its release
  workflow then moves `v0` to the same commit.
- **Evaluation:** the gate's measurements, review-v1, contract-v1 and compare-v1, all linked from the release notes.
