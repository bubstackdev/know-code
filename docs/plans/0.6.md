# KnowCode 0.6 plan

October 27, 2026. Three to four weeks of work.

0.6 makes KnowCode something an automated pipeline can depend on, not only an assistant in one agent's session.
Answers name the exact declaration they mean. A client can discover what KnowCode offers, and where it stops, without
reading prose. A task gets one bounded answer instead of five calls, and many worktrees of one repository share an
index without losing freshness.

What 0.5 and its first automated user left open:

- **Identity by name, not by declaration.** An automated agent pipeline that integrated 0.4.1 found that an answer
  can quote the right source while attaching parts of another declaration:
  - A public type's member list included the members of a same-named private type in another module.
  - Calls to a standard-library member resolved to a same-named member that a local extension declares on a different
    type.
  - Calls satisfied through a protocol were presented as calls to the concrete member.
  0.5.1 fixes the reported cases. Members, extensions and references still associate by name in places, and nothing
  measures how often an `exact` link is wrong.
- **Clients duplicate KnowCode's own definitions.** The single `kc` tool keeps prompt cost low, so a pipeline building
  a safe tool surface reads prose help and keeps its own list of operations, parameters and ranges, and recognises
  errors by English prefixes. Privacy refusals come in two shapes, a tool error and a structured `withheld` entry.
- **Isolation is assembled by hand.** The pipeline gets bound repositories, no discovery, no updates or hooks, and no
  network from an isolated home, forced arguments, its own operation allowlist and a sandbox profile. Nothing
  confirms the scope KnowCode actually runs with.
- **Coverage is global, answers are local.** Status lists the files with parse errors, but an answer about a symbol
  in one of them doesn't say which relationships may be missing.
- **A task takes several calls.** Planning a change takes locate, context, impact and tests, joined by the client,
  each with its own continuation.
- **Every worktree indexes from scratch.** A pipeline running many jobs on one repository pays for indexing and disk
  per job.
- **0.5.0's gate misses** (the strict replay scorer and the history caller questions) are 0.5.1's, not 0.6's.

## Gate

0.6 ships when these pass, compared with 0.5.0 (or the latest 0.5.x), and are published with the release. None makes
a model call.

- **Tool cost per turn** for each profile: no growth beyond what the release notes name and justify. Capabilities
  are served on request and don't add to what's loaded up front.
- **Replay and history gates** as in 0.5: no regression beyond tolerance, scored under both the strict and
  call-site-aware scorers.
- **Identity, against a compiler:** a public set of references sampled from the pinned public repositories, labelled
  by the language's own toolchain (the Swift index store, the TypeScript compiler, Roslyn for C#), not by KnowCode or
  a model. The set is weighted toward names declared more than once.
  - Precision of links KnowCode marks `exact` is at least 0.99, and every wrong one is listed.
  - No link to an indexed declaration where the toolchain resolves outside the workspace.
  - Recall is reported per language.
- **Contract:** every op's capabilities entry matches what the op accepts and returns, checked against the real
  server. Error and refusal codes are stable across the replay. Restricted mode is checked to stay inside its bound
  repositories, write only its own cache, make no network connection, and refuse unlisted operations.
- **Task answers:** a public set of tasks from public repositories' history, labels from git alone. Each task is a
  fix commit's linked issue title or its commit subject; its labels are the files and tests the commit changed.
  - Recall of changed files and tests within the answer's budget is reported against KnowCode's own `locate` alone.
  - The task answer must be higher at equal or smaller answer bytes.
- **Worktrees:** N worktrees of one public repository on a shared base.
  - On a fixed query set, answers match a fresh index of each worktree byte for byte.
  - The freshness cases pass in every worktree: a new untracked file, and a same-size edit with its modification time
    restored.
  - Indexing instructions and disk are reported against N separate indexes.
- **Workspace gate, clean-machine acceptance and an update from 0.5.x.**

No comparative or benefit claim about agents is made from the gate.

## Evaluation

The 0.5 milestone study (public-v3's core tier, full client, about $20) runs after 0.5.0, once the maintainer's
private-workspace check is done. Its result is added here before work starts and can reorder the sections below. The
next milestone study runs after 0.6.

## Order

Identity first: the capabilities, task answers and overlays all carry declaration identities, so they're built on
them. Each change measures its own before and after on the relevant gate set before it merges.

### 1. Identity and coverage

- **Declarations, not names:** every symbol has an opaque identity made of its module, scope and file. Members,
  extensions, conformances and reference targets attach by identity. Same-named declarations in different modules,
  or private ones in different files, never share members.
- **Unknown stays unknown:** a reference that can't be tied to an indexed declaration stays external or unresolved,
  even when a single indexed declaration has its name. A known receiver type that differs from the declaring type
  never links. A protocol requirement reached through a conformance is marked as a witness, not as the concrete
  member.
- **Why this one:** for a link resolved among same-named rivals, `evidence: all` says which rivals were excluded and
  why (module, receiver type, arity, argument types).
- **Coverage in the answer:** an answer that touches a file with parse errors or constructs the extractor doesn't
  read says so: the line and column, and which relationships may be missing there (members, calls, references).
  Status keeps the global list.
- **Swift parse coverage:** the constructs behind most parse errors in the public Swift repositories, ranked, and
  the top ones read.

### 2. Automation-ready

- **Capabilities op:** a machine-readable description of every op, generated from the same metadata as help and the
  tool schema:
  - Its input schema, aliases and ranges.
  - Whether it reads or writes (notes are the only writes).
  - Its evidence presets and output shape.
  - The protocol and schema version.
  Ops that take no query are marked as such. A client builds its tool surface from this instead of copying it.
- **Stable codes:** every error, refusal and incomplete entry carries a machine code (`withheld`, `not_indexed`,
  `indexing`, `cut`, `unsupported`, …) and, for privacy, the same policy metadata. Tool errors, partial answers and
  whole-repository refusals agree. English text stays for people.
- **Completeness, said separately:** answers distinguish graph completeness, source completeness and list
  continuation. A budget summary gives the requested and returned size and what each continuation would cost.
- **Restricted mode:** a server started with explicit repositories and an operation allowlist runs with:
  - No workspace discovery.
  - Explicit config and cache locations.
  - No update checks, hooks or network.
  - A startup reply that states the effective scope.
  A documented headless recipe replaces the hand-built isolation, including the real-git requirement where macOS's
  git shim needs to write temporary files.

### 3. Task-level answers

- **Task context:** one bounded op for a goal written in words. It returns:
  - The files most likely involved, with the source that matters.
  - What depends on them.
  - The tests to run.
  - The questions the index can't settle.
  Each section carries its own completeness and continuation. Test suggestions stay advisory: an unlisted test is
  never presented as safe to skip.
- **Test targets:** declared test targets (SwiftPM, .NET test projects, package scripts) with their test names and
  how to run them, kept apart from relevance ranking.
- **File context:** context on a file lists its top-level declarations with lines, so the next call can select one,
  instead of a short description that sends the client to read the file.
- **Areas on declared structure:** inferred areas overlaid on the package's declared targets and modules, saying when
  a cluster spans modules. Both views stay: declared boundaries and co-change answer different questions.

### 4. Many worktrees, one index

- **Shared base, per-worktree overlay:** worktrees of one repository share an immutable base index at a commit. Each
  worktree's own changes are indexed as an overlay, so a new worktree answers after indexing only its changes. The
  freshness guarantees hold per worktree.
- **Provenance:** an export for durable records, carrying:
  - The full commit, the worktree identity and a digest of uncommitted content.
  - The index generation, extractor versions and the privacy policy's identity.
  - Hashes of each query and result, so the same evidence can be compared later.
  Compact answers in a conversation stay as they are.
- **Cache lifetime:** bases are kept and evicted like other indexes. An overlay is removed with its worktree.

## Not in 0.6

- Windows.
- `path` and `flow` across library boundaries.
- Walking past ambiguous dispatch by default (0.5's measurement: one more labelled place, 15% more rows across
  public subjects).
- A paid agent study per release.

## Release

- **Per pull request:** the usual gates, plus the replay subset.
- **Clean-machine acceptance** on Linux and macOS, including restricted mode.
- **Updates:** a cross-version update from 0.5.x.
- **Evaluation:** the gate's measurements and the 0.5 milestone study are linked from the release notes.
