# KnowCode 0.4 plan

October 26, 2026. Two to three weeks of work.

0.4 makes a session with KnowCode cost no more than one without it, and gives agents answers they don't need to check.
Two public studies now agree on where KnowCode stands. In [0.2's](../../eval/public-v1/results.md) and
[0.3's](../../eval/public-v2/results.md), answers were about as accurate as plain tools (grep, find, read), and
sessions using KnowCode processed about 3.5k more tokens than plain ones. Re-check cost was meant to halve in 0.3 and
rose instead. Most of the rise was one session, but even without it, agents kept verifying clean answers: answers
checked anyway went from 21 to 36. Agents not told about KnowCode used it in 53 of 80 sessions.

0.3's study also showed where its own design fell short:

- **The client never saw KnowCode's instructions.** The study's client drops MCP server instructions, so its agents
  were steered by tool descriptions alone. Unprompted use there understates what a full client sees.
- **The bank tested parity more than advantage.** A quarter of it asks where a name is defined, which grep answers
  well. Recall rested on a single question.
- **Re-check cost was judged on a mean.** One session carried 31% of it, and two runs of one build differed by 40%.

## Gate

0.4 ships when a new public study has been run and published, with every failure and loss reported. Its criteria are
fixed, and published in its protocol, before any 0.4 change is measured. No comparative or benefit claim appears
before that.

**Proposed criteria** (fixed at pre-registration):

1. **Research tokens at most equal** to the plain-tools arm (median paired difference, schemas and instructions
   included), in the arm whose prompt names KnowCode. Missed by 0.2 and 0.3.
2. **Re-check cost halved, judged per question.** The median over questions of re-check tokens per session, at most
   half of 0.3.0's on the same bank. One outlier session can't decide it.
3. **Answer F1 and recall at least equal** to the plain-tools arm, with recall judged over at least eight questions
   whose labels are lower bounds.
4. **Unprompted use** in at least 83% of sessions in a full-client arm, which receives the server instructions as a
   real Claude Code session does. The study's bare-client arm is reported alongside, as a descriptive figure.
5. **Re-checks that change the answer** are reported per run (descriptive). Each one is a KnowCode failure.

**Workspace check** (product, not the study): the maintainer runs 0.4 on a large private workspace. Every repository is
indexed and current without an `index` command, and no answer leaves one out silently. Only pass or fail and the
counts are recorded; nothing from that workspace enters this repository.

## Order

Measure before changing. Week 1 pre-registers the study, runs 0.3.0 as its baseline, and breaks down where a KnowCode
session's extra tokens go. Weeks 1–2 build the changes. Week 3 runs the study on the release candidate, publishes and
releases.

### 1. Cheaper than plain tools

- **Measure first:** for each arm, split a session's tokens into the tool list and instructions paid on every turn,
  answers, follow-up calls (more pages, re-asking), and reads of the source after an answer. Changes are chosen from
  this breakdown.
- **The tool list paid on every turn:** fewer tools advertised up front, or tools a client loads only when it needs
  them, keeping each question's tool one step away. The study's arms show which tools sessions actually call.
- **Answers sized to the question:** the shortest answer that settles it, with the rest a `more` call away. A follow-up
  call costs a turn of context, so only cut what sessions don't come back for, measured on the study's calls.
- **Measured by** criterion 1.

### 2. Answers agents don't need to check

0.3's diagnosis found the growing re-checks were clean answers checked anyway, and reads of the code around a cited
line.

- **The evidence in the answer:** each place an answer names carries the source lines that make it true. For a link
  between repos, the answer shows the request and the route it matched, so re-reading the code adds nothing.
- **Say when an answer is whole:** an answer that names every place says so, and says what was searched, in a form
  short enough not to cost more than it saves.
- **Measured by** criteria 2 and 5.

### 3. A study where KnowCode should win

- **A new bank, public-v3:** weighted toward questions spanning repositories, impact two hops out, and HTTP callers,
  with fewer lookups that grep answers well. Eight or more questions have lower-bound labels.
- **A full-client arm:** Claude Code as users run it, with the server instructions and the plugin, alongside the bare
  arm kept for comparison with public-v2.
- **Robust statistics:** criterion 2 is judged per question. The pilot sizes the bank and run count so that a repeated
  run of one build moves each criterion less than the effect it looks for.
- **Harness fixes, frozen before the baseline.**

### 4. Linking and the real workspace

- **Linking gaps found in 0.3:** route templates per app rather than per repository; default actions (`Index` served
  at its controller's route); clients reached through a typed field (`this.client`); requests whose path comes in as
  a parameter.
- **The 500-repository case:** 0.3's background indexing, checked by the maintainer on a large private workspace, with the
  result recorded as pass or fail.

## Not in 0.4

- Windows.
- History and co-change questions.
- Paused feature targets.

## Release

- **Per pull request:** the usual gates.
- **Clean-machine acceptance:** the script on Linux and macOS, including unprompted sessions.
- **Updates:** a cross-version update from 0.3.0.
- **Evaluation:** the published study is linked from the README and the release notes.
