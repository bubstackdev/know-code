# KnowCode 0.1.1 plan

October 20, 2026. A patch release: fixes for what 0.1.0's release testing found, Homebrew distribution, and the
clean-machine acceptance tooling moved into the repo. No new commands or tools, no answer-contract changes. Larger
work (answers agents don't re-check, cheaper default answers, the public evaluation) stays in 0.2.

Estimated size: three to four days of work, then release testing.

## Must ship

### 1. Updating refreshes the client plugin

**Found:** `knowcode self-update` replaces the binary but not the Claude Code plugin bundle that `knowcode setup claude`
wrote (manifest, hooks, skills). Claude keeps running the 0.1.0 bundle, and its cached copy is keyed by the bundle
version. Any 0.1.1 change to the hook script or the skills would never reach someone who updates.

**Change:**

- On `self-update` success, and when `serve` starts with a registered bundle older than the binary, rewrite the bundle
  for each registration in `integrations.json`. Then run Claude Code's plugin update for `knowcode@knowcode-local`, so
  its cache picks up the new version.
- Keep the existing safety checks: only a bundle and marketplace this install created, at the recorded path.
- If Claude isn't available or the update fails, say so once on stderr, with the `knowcode setup claude` command that
  finishes it. Never fail the update or the server.
- Codex and Cursor registrations name the binary only, so they need no refresh. Confirm that, and say so in the docs.

**Tests:**

- An integration test with the fake `claude` CLI covers an old bundle being refreshed and the plugin update being
  issued.
- A failure leaves a clear message and a working server.
- The real cross-version update from 0.1.0 to 0.1.1 is part of release acceptance (see "Release").

### 2. Workspace-wide answers survive one failing repo

**Found:** a workspace-wide `find`, run outside any repo, failed outright. The cache held an index of a checkout
(an agent worktree) whose directory had been deleted, and listing its files failed: `git ls-files … failed in <dir>:
cannot change to <dir>`. The next run succeeded.

`indexed_roots` already leaves out a gone checkout (no `.git` at its root). The failure came through a path that lists
files before that check: most likely light discovery of a newly configured workspace root, on the first run after the
config changed.

**Change:**

- Reproduce it in a test: index a worktree under a workspace root, delete the directory, change the config, then run
  a workspace-wide query in a fresh process.
- Fix that path.
- Make the general rule hold everywhere a query fans out over repos. A repo that can't be read becomes an `incomplete`
  entry for that repo: `missing_repo` for a gone checkout, `failed` for anything else, each with the repo and the
  error. It never fails the whole answer.

**Tests:** the reproduction above, plus a repo whose `git` call fails for another reason (permissions). Both answer
with the other repos and name the one left out.

### 3. `status` always reports the privacy policy it applies

**Found:** for an indexed repo, `status` and `kc_status` show `privacy` only when the policy blocks something or the
file is malformed (`ops.rs`, "Shown when it decides something"). For an unindexed repo they always show it. So a
repo whose privacy file was read, with nothing blocked, looks the same as one whose file KnowCode never looked for.
That makes a wrong `privacy.file` setting impossible to spot from `status`. That is the one check a team with its own
privacy file name needs.

**Change:** always include `privacy` (`file`: `read` / `absent` / `malformed`, the file name looked for, global level,
`block_at`, blocked paths count). Keep it compact. Add one line to the CLI `status` text.

**Tests:** indexed and unindexed repos, each with an absent, a read, and a malformed file. Also a configured file name
that differs from the default.

### 4. The Bash hook decides in the shell script first

**Found:** 0.1.0's hook matches `Bash`, so the hook script starts the `knowcode` binary for every Bash call: about 32M
instructions just to say nothing for `cargo build`. That is mostly binary startup.

**Change:**

- Have `knowcode-grep-hint.sh` read the hook input and exit at once, unless the tool is `Grep` or `Glob`, or the Bash
  command contains a search word: `grep`, `egrep`, `fgrep`, `rg`, `ag`, `ack`, `git grep`, or `find` with `-name`,
  `-iname`, `-path` or `-wholename`.
- This is a cheap, deliberately loose test. Rust still parses precisely.
- No new dependencies: POSIX `sh` and `case` only, no `jq`.

**Tests:**

- `test-hook.sh` cases show non-search commands exiting without starting the binary (checked with a `KNOWCODE_BIN`
  that records being called).
- The existing search cases still produce notes.

Shipping this depends on item 1.

### 5. Uninstall lets Claude delete the plugin's data

**Found:** uninstall removes the plugin with `--keep-data`, which leaves `~/.claude/plugins/data/knowcode-knowcode-local`.
KnowCode stores nothing there. Claude also keeps an orphaned copy of the plugin in its cache, marked `.orphaned_at`,
for sessions still running.

**Change:**

- Drop `--keep-data`.
- Leave Claude's orphaned cache to Claude's own cleanup.
- Say both in the uninstall section of [usage](../usage.md): what Claude keeps, and why KnowCode doesn't delete it.

**Tests:** the uninstall test asserts the plugin uninstall is issued without `--keep-data`.

### 6. No build-machine paths in release binaries

**Found:** the Linux binaries in 0.1.0 contain `/home/runner/.cargo/registry/src/…/tree-sitter-0.27.1/src/…`. The
assert paths in tree-sitter's C code come through the `cc` crate. `scripts/build-release` remaps paths for `rustc`
only (`--remap-path-prefix`). The paths are the hosted runner's, not personal, but release binaries shouldn't carry
build-machine paths at all.

**Change:**

- `scripts/build-release` also exports `CFLAGS` and `CXXFLAGS` with `-ffile-prefix-map=<cargo home>=/cargo` and
  `-ffile-prefix-map=<checkout>=/src`, appended to any the caller set.
- Add a release-CI check that fails if a built binary's strings contain the builder's home or checkout path.

**Tests:** `test_dist_build.py` gets a C fixture compiled through the wrapper, with no absolute build path in its
object file. The CI check runs on every platform build.

## Should ship

### 7. Homebrew

Restore what #38 removed for 0.1.0:

- `dist-workspace.toml`: `installers = ["shell", "homebrew"]`, `tap = "bubstackdev/homebrew-tap"` and
  `publish-jobs = ["homebrew"]`.
- Regenerate `release.yml` with `scripts/generate-release.py`.
- The CI check that the tap is public and writable.
- The generator's tap commit identity rewrite, and its test.
- `self-update`'s Homebrew detection: "run `brew upgrade bubstackdev/tap/knowcode`".
- The install sections of the README and [releasing](../releasing.md).

Owner steps (see "Owner actions") create the tap repo and the token. If the token isn't in place by release testing,
ship 0.1.1 without Homebrew rather than wait.

**Acceptance:** after the release, `brew install bubstackdev/tap/knowcode` on a clean macOS machine. Then
`knowcode --version`, `knowcode setup claude`, the first query, and `self-update` refusing with the brew hint.

### 8. Clean-machine acceptance in the repo

0.1.0's clean-machine runs used scripts kept outside the repo. Move them in as `scripts/acceptance/clean-machine.sh`,
one script for macOS and Linux, and fix what the runs showed:

- Never start an interactive shell that takes the terminal (`zsh -lic`), which suspended the script twice. Use login
  shells without `-i`, with stdin from `/dev/null`.
- Compare client settings per entry, removing only KnowCode's own entries, never whole keys. The 0.1.0 checker
  reported a false "settings changed".
- Snapshot settings right before uninstall, not before the client is signed in.
- Record two sessions per case, unprompted and then naming the tool. Report `used_knowcode`, tool calls and time to
  the final answer, from the client's transcripts. These numbers are recorded, not gated.
- Cover the installer's PATH change when `~/.local/bin` isn't already on PATH. This was untested on macOS in 0.1.0,
  because the client's own installer had already added it.
- After uninstall, follow its printed removal steps and check that a new shell starts without errors.

Update [first-run acceptance](../first-run-acceptance.md) to use it.

### 9. A flaky test

`ops::tests::coupled_works_on_any_tracked_file` failed once on the hosted macOS runner. The fixture's
`git commit -q -m "infra 0"` exited non-zero, and its stderr wasn't captured. It passed on rerun and in three local
runs, and the test hasn't changed since 0.1.0.

**Change:**

- Have the shared `commit` test helper print git's stderr on failure.
- Run the test in a loop on hosted macOS to reproduce it.
- Suspect a shared test-cache directory being removed by another test, as fixed once before.
- Fix the cause; don't add a retry.

## Not in 0.1.1

- Answers agents don't need to re-check, cheaper default answers, tool-selection work beyond item 4, `fetch-deps`
  and `history deepen`. All of these are 0.2.
- Windows.
- Any comparative claim or evaluation number. The public evaluation is 0.2's gate.

## Owner actions

These need the repository owner's account. Everything else is done in pull requests.

1. **Tap repository.** A maintainer creates the public `bubstackdev/homebrew-tap` with a README, for review before its
   first push.
2. **Tap token.** Create a fine-grained personal access token:
   - Open <https://github.com/settings/personal-access-tokens/new>.
   - **Token name:** `knowcode homebrew tap`.
   - **Resource owner:** `bubstackdev`. If the organization isn't offered, an organization owner first allows
     fine-grained tokens under the organization's Settings → Personal access tokens.
   - **Expiration:** 90 days. Put renewal on the calendar; an expired token fails the release's tap check.
   - **Repository access:** Only select repositories → `bubstackdev/homebrew-tap`.
   - **Permissions:** Repository permissions → **Contents: Read and write**. Metadata becomes read-only automatically.
     Nothing else.
   - **Generate token** and copy it. It is shown only once.
   - If the organization requires approval, approve it under the organization's Settings → Personal access tokens →
     Pending requests.
   - Store it without pasting it anywhere else: `gh secret set HOMEBREW_TAP_TOKEN -R bubstackdev/knowcode`. It
     prompts for the value.
3. **Clean macOS machine** for the Homebrew and cross-version update checks: a machine that has never had KnowCode
   installed.

## Release

- **Gates per pull request:** the usual local gates ([evaluation](../evaluation.md#gates-per-change)) and the public CI
  run.
- **Version:** 0.1.1. The changelog entry is dated on release day.
- **Clean-machine acceptance with the new script:**
  - Linux x86_64. Native if possible; record whether it was emulated.
  - macOS Apple silicon.
- **Cross-version update, new for this release:** on a machine with 0.1.0 installed by the shell installer and set up
  for Claude Code, run `knowcode self-update`. Check:
  - the version;
  - that the plugin bundle and Claude's plugin version are 0.1.1 (item 1);
  - that a new session uses the new hook (item 4).
- **Artifact checks:** each published archive matches its checksum and attestation, and no binary contains
  build-machine paths (item 6).
- **Homebrew acceptance** (item 7), if it ships.
