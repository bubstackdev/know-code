# Accepted product constraints

Moved verbatim from AGENTS.md on 2026-11-12 to keep session instructions small. These accepted requirements remain binding; historical implementation statements describe their original checkpoint. Current release status is in [RELEASE_PLAN.md](RELEASE_PLAN.md), and current stabilization work is in [CODEBASE_REVIEW_0_0_2.md](CODEBASE_REVIEW_0_0_2.md). The user selected stabilization only for 0.0.2; earlier assigned new features move to later releases with timing undecided.


- Know Code is an OSS code-intelligence product supporting embedding, local CLI/MCP, and shared service deployments through a common core.
- Know Code uses Apache-2.0; see LICENSE. Reference clones retain their upstream licenses and are not project implementation.
- Know Code operates locally after dependency restoration, without hosted services. Widely published builds must have zero telemetry, including local usage collection and hidden opt-in collectors. Debug/personal builds may gather unrestricted local diagnostic payloads for future agent bug investigation, without uploads. Automatically rotate diagnostic records and payload bundles under a configurable disk budget; initial design default is 10 GiB per user across workspaces. Record pruned/dropped evidence; rotation never deletes live indexes or source. User-facing errors/status and required index state are not usage telemetry.
- The common core is Rust, with thin .NET bindings using a C-compatible ABI/PInvoke and a native Node-API add-on for Node.js. SQLite in WAL mode is the accepted initial durable fact/text-index store, with bounded graph traversal in Rust, subject to performance gates. Bound reader lifetimes and manage checkpoints; exact reader/cursor mechanism, checkpoint policy, and durability settings remain open. Detailed binding ownership/async/packaging and storage schema remain open.
- Bundle a pinned SQLite build across the coordinator and native library artifacts, including FTS5 support, rather than depending on the macOS system SQLite. Use the same pin/build feature policy for a release; this does not require one physical shared library file. Exact version, Rust binding crate, build flags, and linkage remain open.
- Start with one Rust core crate containing ordinary modules for facts/identity, storage, updates, and queries, plus thin host/native-binding targets. Keep CLI/MCP-only dependencies outside the embedded core's required dependency surface. Split further only for concrete dependency/reuse needs; do not create a crate/plugin/validation layer for every responsibility. Exact target/package names and build layout remain open.
- Support multiple languages without growing separate engines for each language or deployment.
- Use five shared logical fact families across languages: source artifacts, symbols, occurrences, relationships, and analysis reports. Keep a semantic symbol separate from its declaration/use occurrences. This accepts the logical model, not a physical five-table schema, exact fields/encoding, or new abstraction framework; see docs/FACT_MODEL.md.
- Internal source coordinates use UTF-8 byte ranges tied to the exact indexed source version. Convert provider-native coordinates at ingestion and line/column coordinates at API boundaries; never apply a stale range to current disk text. Endpoint convention, line/column encoding, and non-UTF-8 input details remain under design in docs/FACT_MODEL.md.
- Initially retain indexed source text in the workspace SQLite database, sharing identical payloads across targets/generations while preserving distinct artifact origins and compilation ownership. Publication/cleanup follows generation and reader lifetimes. External source blob storage is deferred until a measured need; exact schema/hash/compression remains open. Retain current/pinned/recovery state, not a source-history archive.
- v0.0.1 must support TypeScript and C#. More languages will follow; extract genuinely shared behavior and keep language-specific semantics in narrow adapters.
- v0.0.1 supports macOS on Apple Silicon only (ARM64). Intel Macs and Windows/Linux are outside v0.0.1; later platform timing remains undecided. The user selected macOS 15+, Node 24 and a separately installed .NET 10 SDK for the first ARM64 packaging candidate; older OS versions have not yet been validated.
- v0.0.1 requires compiler-resolved symbols and references using the TypeScript compiler and Roslyn. Syntax-only extraction does not satisfy that requirement; incomplete/unresolved analysis must be reported honestly.
- v0.0.1 analyzes standalone TypeScript files without a tsconfig.json using an inferred compiler configuration. Expose inferred options/origin and coverage limits, use the TypeScript compiler, and do not write synthetic config into the source repository. Exact grouping/default options remain open; a broken explicit project config must not be silently replaced by inference.
- Analyze every declared C# target framework by default in v0.0.1. Keep compilation-specific bindings distinct, share identical source content where practical, and bound worker residency/concurrency rather than silently skipping targets. Unavailable or failed targets must be visible in coverage.
- Analyze one selected C# build context per workspace across all target frameworks. Default to repository/MSBuild evaluation unless explicitly overridden, preserving solution-to-project configuration mappings even when project labels differ. Expose the selected context and effective project configurations in coverage; changes invalidate affected facts through the shared update path. If several solution files are present, require one workspace solution selection for mappings; projects outside that solution still use their own evaluated defaults. Do not expand every solution context, impose a Know Code-wide Debug default or expand every configuration automatically. Policy-v1 workers now evaluate repository/solution contexts; see docs/CSHARP_CONTEXTS.md and docs/WORKSPACE_SETTINGS.md for actual behavior and evidence boundaries.
- Combine equivalent query findings across target frameworks with explicit supporting-target provenance, preserve target-specific differences, and offer target filtering through the shared query operators. Grouping must not merge incompatible identities or fabricate paths by combining mutually incompatible compilation contexts.
- Include test projects/code in the default index; provide shared query filters to include or exclude test code without removing indexed facts. Preserve classification evidence/uncertainty; static test relationships are not proof of execution coverage.
- Local variables and parameters must be queryable symbols too. Keep default graph overviews focused on types/members/callables, with explicit access/filters for finer-grained symbols; do not drop locals from analysis merely to simplify graph presentation.
- v0.0.1 includes generated project source (compiler/source-generator output and available generated clients), labeled with origin/mapping evidence. Compiler-integrated generation is supported; missing external codegen/build outputs are reported as coverage gaps rather than automatically running full builds or external codegen commands. Saved-input-derived documents are distinct from excluded unsaved editor buffers.
- Publish valid partial graphs when saved code has compiler errors, with explicit diagnostics and coverage. Freshness and completeness are separate: fresh partial results must not be labeled complete, and stale prior facts must not be silently merged as current. Analyzer/storage failure is distinct from ordinary compiler errors.
- Automatically restore missing project dependencies using the appropriate package tooling, with visible progress/failures and deduplicated work. Do not restore on every save when dependency inputs are unchanged. Node.js and the .NET SDK are separately installed prerequisites; detect missing/incompatible tools and report actionable errors rather than installing them.
- Honor repository-selected TypeScript versions and .NET SDK selection, reporting missing/unsupported versions explicitly without silently substituting an unrelated toolchain. TypeScript package restoration is dependency setup; Node/.NET SDK installation remains external. Record effective compiler/SDK identities separately from worker/runtime requirements. Supported-version ranges, unpinned defaults, and version-isolation mechanics remain open.
- Third-party dependencies default to external symbol identities/signatures/docs where available, not full dependency-source indexing. Compilers still consume restored dependencies for accurate resolution. Full optional third-party source indexing is deferred without an assigned release; preserve explicit external-analysis boundaries.
- v0.0.1 also requires callers, callees, and dependency-impact queries; these are core product capabilities, not deferred extras. Extract invocation/dependency evidence explicitly, keep references distinct from calls, and report unresolved/possible targets honestly.
- Include compiler-implied property accessor, overloaded operator and conversion calls in callers/callees by default, labeled implicit and filterable. The user accepted this default; it is not a promise to reconstruct every lowered runtime operation. See docs/CALL_GRAPH.md for the implementation plan and current gaps.
- Use explicit, labeled initializer nodes for file-loading/type-initialization calls; the user accepted this representation. Never imply that a field/function-value initializer executes on every later use.
- Impact results return one supporting path per affected symbol by default, with additional paths available on explicit request under shared query budgets. Prefer a compiler-bound path over a shorter path containing possible dispatch. Preserve compilation compatibility and uncertainty; compiler binding is not proof of runtime execution, and one returned path is not proof of uniqueness. Respect query budgets and expose limited search without claiming that a preferred path does not exist merely because it was not found. Exact traversal/tie-breaking mechanics remain open.
- Impact analysis includes possible interface/virtual dispatch targets by default, explicitly labeled, with an exact-target-only filter. Preserve edge/path evidence; a compiler-resolved virtual/interface declaration is not proof of a concrete runtime target.
- Impact traversal follows compiler-backed calls, value references (including field/constant reads), type references, inheritance and imports by default. Label dependency kinds and make them filterable through the shared Rust operators. Preserve compiler evidence and unresolved/external boundaries; textual matches are not dependency edges, and callers/callees remain call-specific.
- Use a hybrid agent API: focused tools plus a bounded structured read-only graph-query operation, both using the same Rust query operators. Keep SQL/private storage details internal; do not build a second execution engine or custom textual query language.
- Default graph results are compact symbols/signatures, relationships, and source locations, with optional bounded source-body inclusion. Apply the same projection/budget semantics across all entry points; included source must match the served generation. Compactness must preserve required freshness, coverage, resolution evidence, and target provenance.
- v0.0.1 MCP uses an agent-launched stdio process; HTTP transport is deferred without an assigned release. The MCP process queries through the same embedded Rust core and shares the persistent coordinator/indexes. Closing an MCP connection must not stop background indexing; worker Protobuf stdio and MCP transport are distinct boundaries.
- Embedding-based semantic code search is deferred beyond v0.0.1 with no assigned release. v0.0.1 focuses on symbol/text search and compiler-backed graph queries; embeddings must not become a required model/runtime dependency for that release.
- Use SQLite FTS5 for initial lexical search in each workspace database, subject to code-search quality/performance gates. Keep search behind shared Rust operators and scope results to the served generation; FTS matches are not compiler-resolved graph evidence. Tokenization/ranking, exact-match behavior, and physical FTS layout remain open; no separate search engine is required initially.
- v0.0.1 requires in-process libraries for both .NET and Node.js; subprocess-only access is insufficient. Both must use the common core. Storage, queries, and graph traversal remain in-process; compiler analysis may use workers through one shared analysis contract. Workers must not duplicate storage or query logic.
- Language workers use versioned Protobuf messages in bounded length-prefixed batches over local stdin/stdout. Share schema/codec infrastructure across providers; exact codec libraries and frame/batch limits remain open. This protocol does not turn embedded graph queries into RPC.
- Consumer/coordinator control uses a local per-user Unix domain stream socket, reusing versioned Protobuf framing/codec infrastructure for registration, jobs, refreshes, and freshness notifications. .NET/Node bindings use the shared Rust control client; graph queries remain in-process.
- v0.0.1 must allow multiple local processes to use the same repository index concurrently (for example .NET and Node/MCP consumers). A persistent local coordinator starts automatically at user login and continues indexing after consumers disconnect, using the same Rust core. Queries remain in-process; detailed ownership, startup implementation, and coordination mechanics remain open.
- The coordinator is the sole workspace-index writer. Run compiler analysis without holding a write transaction across it, then publish completed changes atomically; readers retain their coherent generation. Consumers submit update requests through shared coordinator control, and workers never write the serving index. Exact writer fencing, staging, and recovery mechanics remain open.
- Rebuildable indexes may lose recent indexing progress after power failure; startup must reconcile recovered state with saved source before claiming freshness. Registrations/settings require stronger durability. This permits index progress rollback, not incoherent facts/source or lost settings. Exact synchronous/fsync and recovery mechanisms remain open.
- Automatically rebuild a corrupted derived index, preserving registrations/settings and exposing recovery progress/failures. Reuse the bounded coordinator rebuild path; do not serve data known to be corrupt as stale fallback. Exact detection/isolation, retry/backoff, and damaged-artifact retention remain open; corruption is distinct from version incompatibility, access errors, or resource limits.
- Support both explicit repository registration and parent-folder repository discovery through one durable workspace registry and indexing path. Newly discovered repositories beneath a registered parent automatically register and begin indexing, subject to discovery exclusions and shared resource limits. Overlapping registrations must not duplicate indexing or conflate distinct worktrees. Exact traversal/exclusion rules and discovery timing remain open.
- Parent-folder discovery skips directory symlinks by default. Linked repositories can be registered explicitly, resolving to the existing repository/worktree identity where applicable to avoid duplicate indexes. This discovery policy does not exclude compiler-resolved linked source files; exact alias/canonical-path handling remains design work.
- If a registered repository disappears, retain its index/settings until explicit removal, mark it unavailable, and resume automatically when the same workspace returns. Reconcile saved inputs before claiming freshness. A missing path is not an empty repository or permission to delete retained state; verify workspace identity before reusing an index at a returning path.
- Store indexes and durable coordinator/registry state centrally per user, outside source repositories and temporary/cache-evictable locations. Use one index database per repository/worktree plus a small central registry; all language projects in a workspace feed its shared index.
- Workspace analysis settings use optional checked-in .know-code.json and centrally stored personal settings.json beside the workspace index. Personal fields override checked-in fields; explicit null selects compiler defaults. Only personal settings can grant package-script/hook execution. Settings replacement is whole-object, not a patch. All entry points share coordinator resolution and the existing invalidation path. CPU/memory caps remain separate personal settings. See docs/WORKSPACE_SETTINGS.md.
- Resist code, dependency, and validation sprawl. Prefer shared typed contracts and validation at external boundaries.
- The intended work-scale use case includes hundreds of repositories, C# service architecture, and an Angular frontend. Validate SQLite, cross-repository identity, indexing throughput, and upgrade paths against that workload; acceptance of the initial store is not proof that scale/performance targets are met.
- Whole-estate cross-repository queries target v0.0.2, not v0.0.1. Design v0.0.1 identities/artifacts for that next step without implementing distributed infrastructure prematurely.
- Angular template-to-component references target v0.0.2. v0.0.3 must add Swift and Rust source analysis through the same core/provider contract; do not confuse Rust source support with the Rust implementation language.
- Implement Swift project support in the user-selected order: SwiftPM first, then Xcode. The supplied local repositories contain one saved shared Xcode scheme, AtelierLibraryPhone (app and UI tests); use that for the concrete test case. A general one-scheme/all-schemes policy has not been accepted.
- Xcode iOS analysis must cover both device and simulator code paths. Preserve distinct compilation contexts, source deduplication and target provenance; do not merge incompatible context-specific bindings or graph paths. This is a requirement for the Xcode follow-on, not a claim that Xcode support is implemented.
- Swift defaults to a compatible installed Xcode when no repository pin or explicit toolchain override applies. Honor recognized repository pins and explicit overrides; report conflicts/missing tools without substitution. Use CLT when no Xcode is installed, expose selection/compiler/SDK and coverage gaps, never change global xcode-select or install compilers. See docs/SWIFT_PROVIDER.md for supported pin formats and environment scope.
- The primary v0.0.2 deployment is a local Apple M5 Max workstation, not a shared team server: 64 GB unified memory here, 128 GB at work. Storage layout and Know Code's resource budget remain open; total system RAM is not the application budget. Do not assume the full graph or every compiler workspace stays resident.
- Read docs/DESIGN.md for requirements; proposed architecture and performance targets are not implemented guarantees.
- Exceptional resource efficiency is a product priority. The user's high-end workstations are test environments, not minimum or recommended hardware requirements. Keep baseline operation light; do not justify waste with available RAM/compute. No minimum hardware has been accepted. The user later accepted initial shared background ceilings of two CPU cores and 2 GiB, adjustable per user; these are tuning defaults, not hardware requirements.
- Heavy concurrent video encoding is a normal supported development-workstation workload, explicitly confirmed by the user. Treat CPU contention as an expected acceptance scenario. Measure query responsiveness, indexing progress/freshness, and interference with other work; regular operation must not require an idle/exclusive machine. Under contention, prioritize interactive query responsiveness over indexing freshness. Let background indexing progress more slowly within shared resource limits, preserve fairness across queued workspaces, and report lag as explicitly stale. Scheduling/enforcement mechanics and other numeric goals remain open. Compiler-setup timeouts remain real integration gaps until resolved; passing search probes does not make the full suite green.
- Accepted first contention performance gate: warm, focused symbol/reference lookups returning at most 100 results from an already-current index should achieve p95 <=100 ms during encoding, initially on named TS/Polly fixtures through the native APIs. This is a performance gate, not a new runtime timeout or permission to omit evidence or relabel stale results. Measure full API work per binding, retain tail misses, and keep cold/setup/freshness-wait cases separate; other numeric goals and enforcement mechanisms remain open.
- Resource management is automatic by default, with optional per-user CPU and memory caps. Use shared budgets for coordinator-managed analysis, workers, and caches across repositories/providers; do not multiply limits per repository. If a project cannot be analyzed within a configured cap, stop the affected analysis, report resource-limited, and retain any prior results explicitly stale. Do not silently raise the cap or publish an interrupted stream as a completed partial graph. The user accepted initial two-core/2 GiB shared defaults and 20 ms sampled macOS memory enforcement with possible overshoot; see docs/RESOURCE_CONTROL.md for actual enforcement and remaining limits. Embedded-host allocations outside Know Code are not controlled by these caps.
- Keep the graph as current as possible after files are saved, while preserving low resource use. Saved on-disk state is the permanent freshness boundary; unsaved editor buffers are out of scope, not deferred. Saved uncommitted files still count. Freshness must be visible; do not silently present stale semantic facts as current.
- Prioritize indexing for repositories with active queries or recent saved changes, while ensuring other queued repositories continue making progress under shared resource limits. Reuse the common scheduler across providers; query activity must not trigger redundant analysis or bypass resource caps. Exact fairness/priority mechanics remain open.
- Start with queries over current saved state only. Architect snapshot/fact identity so searchable historical revisions can be added later without redesigning the core; do not retain/index history now or promise a history release. Temporary generations for coherent readers/recovery are not searchable history.
- For upgrades requiring an index rebuild, build a replacement alongside the existing workspace index and cut over only when ready. Compatible old data stays queryable with accurate freshness/coverage during rebuilding. Bound rebuild resources and temporary disk use; do not rebuild every workspace concurrently or delete an index still needed by readers. Exact cutover/compatibility/reclamation mechanics remain open.
- During v0.0.x, compatible library/coordinator versions may coexist; incompatible pairs return an actionable update-required error. Broad backward compatibility is not required before the APIs settle. Explicit compatibility checks must cover relevant protocol/store contracts rather than assume matching or different package versions establish compatibility; exact ranges/handshake remain open.
- In v0.0.1, renames/moves may create new symbol identities. Refactoring continuity is required in v0.0.2, alongside cross-repo queries and Angular template references. Design explicit old/new identity links with evidence, separately from historical graph queries or code-editing features.
- Query freshness policy: wait up to 500 ms by default for pending saved changes, configurable per query and capped by the caller deadline; then return the last coherent result with explicit stale metadata if fresh analysis is not ready. No usable prior index must produce a not-ready outcome rather than fabricated empty/fresh results. The 500 ms bounds freshness waiting, not total query execution.
- Paginated queries stay on one index generation while updates publish. Cursors expire to bound retained state; expiration/invalidation must require an explicit restart, never silently switch generations mid-pagination. Exact cursor mechanism and lifetime remain open.
