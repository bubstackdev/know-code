# Product constraints

- Know Code is an OSS code-intelligence product supporting embedding, local CLI/MCP, and shared service deployments through a common core.
- Know Code uses Apache-2.0; see LICENSE. Reference clones retain their upstream licenses and are not project implementation.
- Know Code operates locally after dependency restoration, without hosted services. Widely published builds must have zero telemetry, including local usage collection and hidden opt-in collectors. Debug/personal builds may gather unrestricted local diagnostic payloads for future agent bug investigation, without uploads. Automatically rotate diagnostic records and payload bundles under a configurable disk budget; initial design default is 10 GiB per user across workspaces. Record pruned/dropped evidence; rotation never deletes live indexes or source. User-facing errors/status and required index state are not usage telemetry.
- The common core is Rust, with thin .NET bindings using a C-compatible ABI/PInvoke and a native Node-API add-on for Node.js. SQLite in WAL mode is the accepted initial durable fact/text-index store, with bounded graph traversal in Rust, subject to performance gates. Bound reader lifetimes and manage checkpoints; exact reader/cursor mechanism, checkpoint policy, and durability settings remain open. Detailed binding ownership/async/packaging and storage schema remain open.
- Bundle a pinned SQLite build across the coordinator and native library artifacts, including FTS5 support, rather than depending on the macOS system SQLite. Use the same pin/build feature policy for a release; this does not require one physical shared library file. Exact version, Rust binding crate, build flags, and linkage remain open.
- Start with one Rust core crate containing ordinary modules for facts/identity, storage, updates, and queries, plus thin host/native-binding targets. Keep CLI/MCP-only dependencies outside the embedded core's required dependency surface. Split further only for concrete dependency/reuse needs; do not create a crate/plugin/validation layer for every responsibility. Exact target/package names and build layout remain open.
- Support multiple languages without growing separate engines for each language or deployment.
- Use five shared logical fact families across languages: source artifacts, symbols, occurrences, relationships, and analysis reports. Keep a semantic symbol separate from its declaration/use occurrences. This accepts the logical model, not a physical five-table schema, exact fields/encoding, or new abstraction framework; see docs/FACT_MODEL.md.
- Internal source coordinates use UTF-8 byte ranges tied to the exact indexed source version. Convert provider-native coordinates at ingestion and line/column coordinates at API boundaries; never apply a stale range to current disk text. Endpoint convention, line/column encoding, and non-UTF-8 input details remain under design in docs/FACT_MODEL.md.
- Initially retain indexed source text in the workspace SQLite database, sharing identical payloads across targets/generations while preserving distinct artifact origins and compilation ownership. Publication/cleanup follows generation and reader lifetimes. External source blob storage is deferred until a measured need; exact schema/hash/compression remains open. Retain current/pinned/recovery state, not a source-history archive.
